## Four stages per tool and one choice per slot

Each JSON tool record has these four independent stages:

1. **Final candidate:** upstream quality, full source pin, primary locators and the G5 catalog row. G5 is PENDING here. Prior documented choices are context, not newly accepted final candidates. Stage 1 flags any alternative for the same slot.
2. **Wiring:** the vendor clean installation and native integration/inverse sources, exact version, per-session PSS and shared-copy boundary. Installation commands are references only. No installation or wire change runs in B. Shared HTTP is preferred only after its source/runtime scope is qualified; a shared backend does not erase a per-client frontend.
3. **Fresh-session evidence:** a natural task for the owning role, with no tool names in the task text, matched to native client and counters. The JSON provides unexecuted examples. Incidental rolling use or the unpaired role trial does not fill this gate.
4. **Invoke measurement:** the hourly record against the named 2026-10-08 baseline, preserving scope. The selected snapshot is dated below; its baseline binding/delta is unmeasured.

A final candidate with low use moves to **WIRE**, never RETIRE for low use. An outranked item can leave only with a named better-evidenced same-job replacement under rule 5 or documented inability to install. No such removal is made here. **KEEP** requires organic-use evidence at stage 3 or 4 and a valid stage 1 candidate; no unknown field is silently passed.
