## What is definitive

The dated baseline is the current decision for the stated requirement: selected
repositories, source identity, evidence, alternatives, limits and the comparison
that could change it. An accepted native operation is stronger than installation
or source review for that operation. It does not automatically prove superiority
on other tasks. Supporting tools and optional components retain those roles.

The full public-star snapshot is reconciled against the repository index.
Historical star flags retain their original date; current membership comes from
the [latest retained snapshot](../catalogs/landscape/upstream-snapshot.json).
Awesome lists and community best practices are candidate discovery sources.
Their selected sections and pinned source reviews are recorded; every link inside
every list has not been independently tested. Stars, novelty and agreement do
not replace a task comparison.

## Resume in six steps

1. Record the checked-out commit and preserve uncommitted work. Read `AGENTS.md`,
   [adoption/manifest.json](../adoption/manifest.json) and the small research queue.
2. Choose one requirement and layer. Read its current choice, pinned upstream
   source, actual receipts, remaining limitation and replacement criterion.
3. On a new PC, use the [adoption guide](../adoption/README.md). Start with
   `foundation-cpu`; add only profiles needed by the task. Verify native sign-in,
   selected tool discovery and a useful task on that host. Old receipts are
   reference evidence, never the new machine's passed status.
4. Check current primary documentation and the named discovery inventories for
   the demonstrated gap. Inspect original source before adopting a challenger.
   Do not reinstall whole packs or change native models merely because they are new.
5. Freeze a small representative input set, expected outcomes and failure cases
   before comparing. Reuse supported upstream commands. Keep source recovery,
   failed attempts, actual model identity when returned, complete usage categories
   and an independent review. Missing metadata stays unknown.
6. Update the affected canonical decision, research queue and dated task record.
   Register new candidate arrays through the existing index command, regenerate
   the HTML and hashes, run relevant checks and inspect the published commit's CI.

Use [adoption/update.md](../adoption/update.md) for exact existing refresh and
validation commands. Public task records belong in Git. Private host paths,
accounts and scoped ai-memory remain private; transfer selected application data

## Continue after a provider usage limit

Before a quota interruption, checkpoint the selected requirement, recommendation
versus accepted configuration, exact source pins, actual receipts, failed attempts,
unknown usage and the next bounded action in the layer's existing task record and
research queue. Pass those references in cross-session and worker handoffs. Resume
the same selected account, model and effort after the provider confirms allowance.
A new conversation or context compaction alone does not establish a quota reset.

Use a provider's available native reset when an eligible limit is reached. Codex
0.159.2's installed protocol schema exposes `account/rateLimits/read` and
`account/rateLimitResetCredit/consume`. The latter consumes an earned reset and
requires an idempotency key; reuse it for retries of the same redemption, then
read rate limits again. Account eligibility stays unknown until a native read;
the schema check itself did not query this account or redeem anything.
[Official OpenAI documentation](https://learn.chatgpt.com/docs/app-server),
[installed schema and pinned source evidence](../evidence/artifacts/memory-runtime-resolution-20260930/provider-quota-capability.json).

Claude's eligible reset offer is in Settings > Usage > Resets on its web or
Desktop client. The official article says the button is unavailable in the
Claude Code terminal/IDE. When no applicable reset is available, continue after
the provider's recorded allowance reset time.
[Native Claude reset](https://support.claude.com/en/articles/17007452-what-is-a-limit-reset).

On resumption, refresh only the selected layer's changed client/release/source

not qualify failed-job recovery. Load security guidance for a matching requested
security task; installation is not a completed audit. Existing native worker,
workflow and recovery receipts keep their individual scope. A matched task result
is needed before changing a runtime or model default.

## A bounded stopping rule

Research saturation means exhaustion of a **named candidate set for frozen
requirements and a date**. It requires complete layer decisions, candidate and
omission records, representative comparisons, needed target-host lifecycle
evidence, independent review and a dated closure record listing residual risks.
The current queue does not claim that all those comparisons are complete.

Stop a review wave when its bounded set is resolved and no material supported
gap remains. Reopen it for a changed requirement/platform, a credible missing
capability, a retained failure or a new comparison that changes the result.
Do not endlessly add repositories to increase a count. This package provides
continuation instructions; it creates no unattended research, service or schedule.

Sweep-over-sweep results are recorded in the append-only
[saturation ledger](../catalogs/saturation/README.md). It counts consecutive clean
sweeps per layer and names saturation candidates, which are inputs to closure,
never closures: a layer still closes only through this queue's `closure_refs`. Its
weekly workflow (`.github/workflows/saturation-tracking.yml`) calls no model; it
updates one tracking issue listing the due layers, and a person starts each sweep
([recipe](../recipes/saturation-sweep.md)), so the statement above still holds.
