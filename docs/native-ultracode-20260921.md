# Native Ultracode qualification and next gaps

The native Workflow and same-host cross-session messaging paths now have actual
execution evidence on Claude Code 2.1.278. No additional orchestration package
was installed. The [portable recipe](../recipes/claude-native-ultracode.md)
contains supported commands and the task-to-model starting policy.

## Observed execution

Fable 5.1/xhigh launched a native Workflow with two explicit workers: Sonnet
5/medium for an evidence inventory and Opus 5/high for independent constraints.
Child assistant records confirmed those actual model/effort identities. Both
completed, their runtime overlapped by 37,751 ms, and the native journal held
two starts and two returned results. All 88 recorded hook responses succeeded.
The coordinator collected the results and reconciled selected source claims.
The script was generated by native Claude and retained privately; its live host
paths were not published as a portable workflow.

The same Fable session resumed at high effort as a native background session. It
discovered the named Sonnet peer, sent one challenge and subscribed to a one-shot
idle notice. The recipient performed an actual source Read, replied once, and
the coordinator verified source lines 70–83. The independent transcript audit
confirmed failure exit at line 78 and verified-partial move at line 80. The idle
notice arrived automatically. No other peers were messaged and no repository
files were edited in that phase. The worker read the whole 207-line source file;
its claim of a focused read was imprecise.

The native agent dashboard rendered Fable 5.1, Ultracode dispatch defaults and
two completed tasks. Dedicated Windows Terminal profiles were added for Fable
Ultracode and the native agent dashboard, preserving existing profiles and
permissions. The dashboard was opened for the user. The existing Grafana view
responded successfully; its worker rows remain coordinator checkpoints rather
than live native discovery.

After background-session resume, native `/workflows` restored the completed
gap-audit run and rendered both phases as 1/1 complete, with two total agents,
an 80.3k rounded token display and approximately 82 seconds. This is actual
history/dashboard recovery, not a new run or proof of pause/resume mid-execution.

## Findings retained and resolved

- Sonnet incorrectly called four exercised MCPs connected-only and described
  prior single-Agent dispatch as unexercised. The coordinator corrected both in
  the resumed session. Only jCodeMunch and Claude Docs had been connected-only;
  native Workflow and task-matched multi-worker dispatch were the new paths.
- Sonnet retried once after a StructuredOutput schema error. Both worker outputs
  exceeded the requested 250-word contract: 297 and 286 whitespace-separated
  words across string values, despite smaller self-reported counts. Opus made
  five word-count calls. Native completion did not establish optimal efficiency.
- The coordinator corrected an overly narrow grep being reported as a broad
  absence. Its blanket statement that read-only workers cannot run checks was
  also too broad: these workers did run read-only checks. Document agreement
  does not independently establish runtime behavior.
- Two native success events share cumulative model usage. They must not be
  added as independent complete runs. No causal token-saving percentage or
  lowest-cost/highest-quality model combination is established.

The native pipeline worked; the independent review was necessary to catch
content errors. That is the reason acceptance is based on source and behavior,
not consensus or a successful process exit.

## Persistent changes and next steps

The short source-first rule was added to the canonical harness policy and
portable Claude core, then deployed to native Claude and native/Desktop Codex
instructions. Current ecosystem skills now distinguish the new Fable evidence
from older exclusions. The existing daily maintenance heartbeat retains its
schedule and scope but now explicitly researches current native features and
upstream alternatives, verifies returned results and avoids noisy polling.

Priorities after this qualification:

1. Evaluate the routing policy on one real implementation task with an owned
   worktree, independent acceptance tests, total usage and elapsed time. Compare
   a simple baseline; do not assume fan-out improves quality or cost.
2. Qualify native Workflow pause/resume, cancellation, missing-worker results
   and writing-worker integration for the intended task. Earlier ordinary-worker
   recovery does not automatically qualify this runtime.
3. Observe the next existing maintenance trigger and its useful persisted
   result. Cross-host messages, post-reboot scheduling and ai-memory cross-project
   mailbox claim semantics remain separate acceptance tasks.

Current observations do not establish every optional SDK, broker-paper lane,
restricted custom role, cloud channel or future machine. The requested native
dispatch and local messaging paths are qualified within the recorded bounds.
