## Historical wording that must not become current instructions

The [runtime target](../catalogs/us-equities/runtime-target.json), [installed stack](../manifests/stack.json) and [readiness reconciliation](foundation-rd-readiness.md) govern current selection. Preserve dated failures and old source pins; correct misleading present-tense consumption through clear overlays rather than rewriting history.

1. **LEAN versus Nautilus.** The September 19 engine cards still label LEAN and its Alpaca brokerage as defaults, Nautilus as an alternative and IBKR as a possible future choice. The engine catalog now explicitly declares that snapshot historical. Current target selection is Nautilus 2.0.0rc5 with native IBKR and a separate Alpaca path. Recommendation: every generated current-selection view must apply that target and retain LEAN's comparison evidence; do not flatten the historical default labels into an installation list.
2. **Alpaca source review versus later execution.** The historical data card says no account, data request or order was exercised by that review. Later authenticated-data and paper receipts qualify their bounded operations. Recommendation: show the original review scope and later acceptance side by side. The paper smoke belongs to the separate alpaca-py lifecycle, and must never be attributed to the LEAN Alpaca or Nautilus IBKR adapters.
3. **Proposed data tools versus accepted runtime.** DVC and Pandera are labeled default in source-review cards, but those cards do not establish native installed dataset/schema acceptance. Recommendation: present them as unqualified implementation candidates when showing current runtime readiness; keep dataset identity and validation requirements without inventing package execution.
4. **Current pins versus historical pins.** The September 19 memory card names ai-memory 2.3.1; current stack/recipes retain later qualified versions. Historical Nautilus and skfolio snapshots likewise differ from the current target and accepted study. Recommendation: obtain installation pins from current component/runtime records and source-review pins from the historical card, with separate labels.
5. **Dagu and Restic acceptance growth.** Dagu's historical conditional label coexists with later selected local workflows; the early Restic card describes static reference files, while application-state restore receipts now exist. Recommendation: surface those later scopes without claiming all workflows recover in flight or that same-host restore is independent disaster recovery.
6. **Old access failures are dated facts.** The earlier SEC acquisition failure and earlier native-account allowance failures remain valid for their attempts. Later corrected acquisition/native paired results qualify later attempts only. Recommendation: render a dated progression; neither erase the original failure nor use it to claim the current account or endpoint is universally unavailable.

No canonical historical catalog was mutated for this synthesis. The new decision file provides the present-day interpretation and the existing full cards retain the detailed reviewed source pins, prospective commands and limitations.

## Adoption boundary

A catalog decision is neither an installation receipt nor authorization to trade. Follow [new-machine adoption](../adoption/README.md) for Linux/WSL x86_64 and collect the target host's own client, scoped data, service and recovery evidence. The clean-userspace and hosted Linux token-tool checks are useful installation evidence for named subsets; they do not qualify the whole ecosystem on another physical PC.

The [acceptance evidence policy](acceptance-evidence-policy.md) remains the standard: unchanged upstream tests, native operations, local integration checks, synthetic fixtures, independent observations and structural validation make different claims. Repository counts, popularity, reviewer agreement and version recency are not comparative performance evidence.
