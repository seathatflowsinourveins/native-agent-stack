# OpenHands worker isolation: per-attempt internal network and a pinned /v1 allowlist proxy (2026-09-28)

**Scope.** This record covers three things:
- network isolation for the OpenHands runtime worker
  ([README, Security posture](../../blueprints/runtime-workers/openhands/README.md#security-posture)),
  in the SWE-bench mode built by the PR #425 takeover (phase 2) and in the resolver mode that a
  follow-up PR adds;
- the ruleset variants for the resolver's agent branches;
- a scoped narrowing of one clause of the 2026-09-25 host-request-lane decision, for the resolver
  lane only.

It replaces the phase-1 DOCKER-USER firewall contract. The source is the coordinator's phase-2
research synthesis of 2026-09-28, which is not committed. Each finding used here is restated with
its own source, and a source the build did not re-read is labelled as reviewed in that synthesis.

**Chosen: O1.** Each attempt `S=<run-id>-<arm>` gets its own resources:
- **`$S-int`,** created with `--internal`, IPv6 off and gateway mode `isolated`. Besides the
  proxy, which joins it as `gw`, only the agent-server and the P1/P2 probe container join it.
- **`$S-gw`,** a normal bridge network used only by the proxy's upstream side and the P0 probe
  container.
- **A pinned nginx-unprivileged proxy** on both networks. As `gw:8081` it forwards three exact
  `/v1` routes with fixed methods, fixed upstream URIs and a fixed header set to one arm's gateway
  port on 10.0.2.2. The host's loopback ingress (`127.0.0.1:<port>`) reaches the proxy's 8080,
  which forwards to the server. The agent can reach that listener too, as `gw:8080`; it leads
  only to the agent's own server, and its access log keeps time, method and status only.
- **OmniRoute stays unchanged:** no login, password or management key is added. The model's
  bearer stays the placeholder `local-loopback`, and `OMNIROUTE_API_KEY` is never sent.
- **The only secret is a per-attempt agent-server session key.** It is generated by the host,
  kept in two owner-only files and deleted after confirmed removal (plan item E2).
- **Before the first conversation,** a P0-P2 probe receipt must be at most 900 seconds old and
  bound to the live network and container IDs, and its counts must re-derive a pass. The
  dispatch gate enforces this. It also requires the host-owned `<state>/stage-gates.json`, in
  which the coordinator records P3 (and P4 and P5 for engines-on), the G2 scans of both pinned
  images and G5. The file stays absent until those gates are observed live, so dispatch start
  refuses until then. The gateway build a probe ran on is recorded, not checked against the
  running build.
- **Official grading has no network.** Every grader container is created with network mode
  `none`, "No networking for this container" (docker/docker-py@7.1.0
  `docker/models/containers.py:686-694`). The adapter refuses any other mode, any SDK create body
  without it, and any created container whose inspect shows another network; that container is
  removed, not graded. moby/moby@docker-v29.8.1 records the mode as the single network `none`
  and refuses to connect such a container elsewhere (`daemon/create.go:251`,
  `daemon/container_operations.go:202-204,363-406`). This fails closed: an evaluation step that
  needs to download fails, so the verdict is an offline verdict
  (SWE-bench@v4.1.0 `test_spec/python.py:443-444`, `test_spec/test_spec.py:55-60`).
- **G5, the gateway provider surface, is checked at every start (repair R3).** The gate reads
  each OmniRoute store the arm reaches, read-only: the provider column, the routing-combo count
  and two named settings keys. It refuses unless every provider the store can serve is in the
  host file's allowlist for that store's arm (control `codex`; engines-on
  `openai-compatible-responses-*`, plus the 20128 store it forwards to). OmniRoute serves
  no-auth and anonymous-fallback providers without a provider row, unless settings disable them
  (`src/sse/services/auth.ts:739-800,1193-1201` at 045aa81f3). Some of these providers have
  subprocess executors, so the gate requires every one to be disabled by id or alias. Routing
  combos are refused. The stage-gates file must also carry the coordinator's G5 record.

**What this design establishes, and where it stops (scoped in the repair round, C9).** None of
it has been observed live; the P0-P2 receipt and the stage-gates records are the operational
holds. It has three parts, and only the first two hold by construction:
- **The agent-server.** Its only standing peer is the proxy; the P1/P2 probe joins `$S-int` only
  while a probe runs. Three routes reach OmniRoute, and `gw:8080` reaches only the agent's own
  server. This does not depend on OmniRoute's authentication state, and it covers the other
  host-loopback listeners, not only OmniRoute.
- **Grading.** Grader containers have no network at all (repair R1), so a model-written patch
  runs offline when it is graded.
- **What the three routes reach.** The request body selects the model, so the providers behind
  the routes are bounded by G5's check of each store at every start (repair R3). That is a check
  of gateway state, which can change after the check, not a property of the topology.

Gateway settings cannot provide the first two parts. The synthesis reviewed these points at
OmniRoute@045aa81f3, and this build did not re-read them:
- With `requireLogin=false`, every management route that is not always-protected is anonymous for
  loopback peers (`policies/management.ts:99-103,253-266`; `apiAuth.ts:451`).
- With `requireLogin=true` and no password, a loopback caller can still post `requireLogin: false`
  (`require-login/route.ts:40-42,89-93`).
- `OMNIROUTE_API_KEY` is checked only after that bypass (`apiKeys.ts:1374-1399`;
  `management.ts:261-266`).

In addition, the container reaches host-loopback ports as 10.0.2.2 on this host
(`DOCKERD_ROOTLESS_ROOTLESSKIT_DISABLE_HOST_LOOPBACK=false`; moby/moby@a46e6fa7
`contrib/dockerd-rootless.sh:23-24,170-173` shows the upstream default). SDK v1.49.6 makes its LLM
calls inside the container.

**Alternatives considered:**
- **OmniRoute split-port mode** (`API_PORT`/`API_HOST`; `.env.example:199-203`;
  `src/lib/apiBridgeServer.ts:16-24,44-56,184-207,244`, as reviewed in the synthesis). Not
  selected, for four reasons:
  - the dashboard listener stays on `127.0.0.1:PORT`, which containers reach as 10.0.2.2;
  - the bridge forwards the raw request URL to a loopback hop after a prefix check, so
    `/v1/../api/settings` is untested;
  - it also passes `/api/oauth/*` and `/callback`;
  - enabling it restarts the shared gateways.

  It remains a candidate upstream target behind the proxy, as defence in depth.
- **DOCKER-USER rule to `10.0.2.2:<gateway port>`** (the phase-1 contract; docker/docs@4e9a5751
  `content/manuals/engine/network/firewall-iptables.md:22-24,48-95`). Rejected as the primary
  control for three reasons:
  - the same port serves `/api/*`, so a layer-4 rule cannot separate the client API from
    management;
  - where the rule sits in the rootlesskit namespace is unprobed;
  - the rule is lost on a daemon restart.
- **O2, a third OmniRoute in a container on the run network.** A fallback only, as a second
  layer behind O1.
- **O3/O4, `requireLogin=true` or an environment key on the gateways.** Rejected. The loopback
  bootstrap write disables login again, and only a password closes that. Both options also change
  the shared gateways for every other client.
- **O5, LLM calls made from the host.** Not supported at SDK v1.49.6.
- **O7, X-Forwarded-For marking alone.** Rejected on its own. It could be added as a later layer
  once the gateways' IP-filter state has been read. Today the proxy passes no X-Forwarded-For.
- **Daemon-wide `--disable-host-loopback`.** Rejected. It would cut off every container, the
  proxy and cognee-live included, and leave the host's non-loopback addresses reachable.

**Overturn (O1):**
- **Stop and reopen this choice, with no fallback to plain `--internal`,** if either of these
  happens:
  - `network create` rejects gateway mode `isolated` under rootless Docker 29.8.1;
  - P0-P2 fail on the live topology.
- **P3 or P5 contradicts the allowlist.** This covers two cases:
  - P3 shows the header allowlist breaking request-body framing or streaming;
  - P5's access log shows that the SDK needs a path outside the three routes.

  In either case, add only a probed route, or reopen the choice.
- **Split-port proves simpler.** Reopen if a probe shows split-port plus a layer-4 rule that
  allows only `10.0.2.2:<API_PORT>`, and that combination blocks `/api/*` for the agent,
  including dot-segment and `%2e` variants, with fewer moving parts than O1.
- **Graders need a network.** Replace mode `none` only with a separately probed internal network
  for graders, backed by its own P0-P2-style receipt.
- **G5 needs a routing combo, or OmniRoute changes its row-less providers.** For a combo, resolve
  its targets against the allowlist rather than refusing. For a gateway upgrade, re-read the
  no-auth and anonymous-fallback lists from its source before the next start.

## Agent-branch ruleset (resolver mode; applied by the owner)

**Chosen:** one repository ruleset, with main ruleset 23739774 and tag rulesets 23829417 and
23859358 unchanged:

```json
{
  "name": "Agent branches: no history rewrite",
  "target": "branch",
  "enforcement": "active",
  "bypass_actors": [],
  "conditions": {"ref_name": {"include": ["refs/heads/openhands/*", "refs/heads/openhands/**/*"], "exclude": []}},
  "rules": [{"type": "non_fast_forward"}]
}
```

The resolver acts through the admin owner login, so any bypass would free it too. Only rules
with no bypass bind it. Two patterns are needed. "Because GitHub uses the File::FNM_PATHNAME
flag for the File.fnmatch syntax, the * wildcard does not match directory separators (/)", and
`qa/**/*` is the documented form for deeper names (docs.github.com
creating-rulesets-for-a-repository, fetched 2026-09-28). Whether `**/*` also matches single-level
names is unverified. The owner creates the ruleset with one POST and edits it later with PUT by
id, following the repository convention (`docs/github-automation.md:479-481,493-494`).

**Alternatives considered:**
- **A deletion rule with no bypass.** Not chosen. It would stop the resolver deleting and
  recreating a branch, but it would also block post-merge automatic deletion and the owner's
  cleanup: "Branch protection rules and repository rules can also prevent branches being
  automatically deleted" (docs.github.com managing-the-automatic-deletion-of-branches, fetched
  2026-09-28). That path is closed on the client side instead: no ref DELETE, `--delete` or
  `:ref` refspec.
- **A deletion rule with an admin bypass.** Rejected, because it protects nothing: the resolver
  is the admin.
- **Approval counts, last-push approval or update restrictions.** Rejected. Owner and resolver
  are the same identity, so these rules either block the owner or, with a bypass, free the
  resolver.
- **Push rulesets with path restrictions.** Unavailable here: "Push rulesets are available for
  the GitHub Team plan in internal and private repositories" (docs.github.com
  available-rules-for-rulesets, fetched 2026-09-28). The hard-deny paths live in the resolver's
  patch validator instead.

**Overturn:**
- **A receipt shows the resolver deleting or recreating an `openhands/*` ref.** Add a deletion
  rule with no bypass and accept manual cleanup.
- **Never-merge, no-ready, no-tag or no-workflow-edit must hold on the server.** Move to a
  dedicated GitHub App identity without the workflows permission, plus a pull-request approval
  rule on main with an owner bypass. That is not a remedy for container egress.
- **Push rulesets become available for this repository.** Move the hard-deny paths to the server.

## Scoped narrowing of the host-request-lane clause (resolver lane only)

`docs/decisions/2026-09-25-host-request-lane.md:176-178` rejects "Auto-executing requests with
`claude -p`. That would feed untrusted issue text to a model that has tools. Anyone can open an
issue on a public repository, and even the owner's text is data, not an instruction. Execution
stays coordinator-run."

The resolver lane does not simply conform. Even when the coordinator starts each run, a model
with tools acts on owner-authored issue text. This record therefore narrows the clause for this
lane only. Owner-authored issue text may reach a model with tools only when all three conditions
hold:
1. the coordinator starts the run and declares its scope;
2. the model's tools are contained by the O1 topology above, the G5 provider check and the
   resolver's GitHub harness. Their only network is the proxy: three routes reach OmniRoute,
   which serves only allowlisted providers when G5 passes, and `gw:8080` reaches only the
   agent's own server. They hold no credential other than their own server's session key, reach
   the host only through those routes, and their patch is graded with no network;
3. a validated patch is the only output.

**Overturn, reverting to coordinator-only execution,** if any of these happens:
- a containment probe or check fails: P0-P2, G5, or the resolver acceptance check A7;
- an outgoing-text guard finding or an unowned path appears in any run;
- the lane gains a trigger other than an explicit coordinator invocation. A timer, label or
  webhook needs its own dated record.

The narrowing takes effect only when this record merges, and the owner may reject it. The
SWE-bench mode reads no issue text and needs no narrowing.

### Resolver-mode amendment (proposed 2026-09-28, pending the owner's decision)

Independent review of the resolver's stage 2 found that resolver mode does not meet conditions 2
and 3 as written (`blueprints/runtime-workers/openhands/RESOLVER.md`, "The push runs the model's
code in CI"):
- **Condition 2.** The driver grades nothing. It pushes the agent's commit to a branch of this
  repository and opens a draft PR. main's `pull_request` workflows then run repository code from
  the PR's merge commit, including files in the owned paths, on GitHub-hosted runners whose
  egress is audited, not blocked. So the patch runs with network.
- **Condition 3.** Besides the validated patch, the PR body publishes up to 6000 characters of the
  agent's final message, fenced and guarded, and its resolvable SOTA lines.

The bounds were read at origin/main b0fb65b4 by parsing every workflow file
(`blueprints/runtime-workers/openhands/evidence/stage2-repair-fail-first.txt`, "observations").
11 of the 20 workflows run on `pull_request`. Each sets `contents: read` at the workflow level,
and none uses a secret other than `GITHUB_TOKEN`. No workflow uses `pull_request_target` or
`workflow_run`, and the only jobs with a write scope among the 11 skip `pull_request`. Check
results on `openhands/*` are model-controlled and are not evidence.

The owner decides between two options:
1. **Accept CI execution** for resolver mode within those bounds, re-checked whenever a workflow
   changes, and accept the final message as a second, guarded output. The resolver as built
   needs no code change for this option.
2. **Push agent branches to an owner fork**, so that PR runs get no secret and a read-only token
   whatever a workflow declares. This is the review's proposal. GitHub states the token and secret
   limits in [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows),
   "Workflows in forked repositories" (read 2026-10-03): "With the exception of `GITHUB_TOKEN`,
   secrets are not passed to the runner when a workflow is triggered from a forked repository. The
   `GITHUB_TOKEN` has read-only permissions in pull requests from forked repositories." That
   sources the guarantee for `pull_request` runs from a fork.
   - **Holder: undetermined.** This repository's owner is the User account
     `seathatflowsinourveins`. The repository is public and has no fork
     (`gh api repos/seathatflowsinourveins/native-agent-stack`, read 2026-10-03). GitHub's
     [Forks](https://docs.github.com/en/pull-requests/reference/forks) reference, "Which
     repositories can be forked?" (read 2026-10-03), says: "You can fork any public repository: To
     your personal account; To an organization where you have permission to create repositories."
     It says nothing on forking one's own repository. The holder is therefore an organization the
     owner creates or a second account. Which one it is changes the push identity, the fork's
     ruleset and the `--head <holder>:<branch>` value.
   - **A harness change.** The resolver as built pushes to and opens PRs only in this repository.
     `blueprints/runtime-workers/openhands/resolver/gh_harness.py:44` fixes `REPO`. `op_push`
     (`blueprints/runtime-workers/openhands/resolver/gh_harness.py:241-254`) pushes only to
     `origin`, and `push` (`blueprints/runtime-workers/openhands/resolver/gh_harness.py:704-709`)
     refuses unless the origin push URL equals `ORIGIN_URL`. `op_pr_create`
     (`blueprints/runtime-workers/openhands/resolver/gh_harness.py:257-259`) and its allowlist
     entry (`blueprints/runtime-workers/openhands/resolver/gh_harness.py:448`) pass
     `--head <branch>` in this repository. `check_repository`
     (`blueprints/runtime-workers/openhands/resolver/gh_harness.py:627-628`) requires `full_name`
     to equal `REPO`, and `branch_rules`
     (`blueprints/runtime-workers/openhands/resolver/gh_harness.py:684-689`) reads this
     repository's rules. The ruleset section above binds only this repository's `openhands/*`
     refs.
   - **Before a first run**, option 2 therefore needs a separately reviewed change: a fork remote
     and push-URL check, `gh pr create --head <holder>:<branch>`, the branch-rules lookup and a
     `non_fast_forward` ruleset on the fork, and its own independent review.
   - **Condition 3.** A fork does not change what the PR body publishes. `build_pr_body`
     (`blueprints/runtime-workers/openhands/resolver.py:547-550`, `:590-592`) includes the final
     message wherever the branch lives. Under option 2 the owner either accepts the final message
     as a second, guarded output, as in option 1, or has it dropped from the PR body, which is a
     further change to `build_pr_body`.

Neither option blocks CI egress. With a fork, main's `pull_request` workflows still run the pushed
code on the same GitHub-hosted runners, whose egress is audited, not blocked. Either option can
add an egress block to the PR jobs that run repository code; that is a workflow change outside the
resolver PR. Until the owner accepts one option, and for option 2 until its harness change
has passed its own review and landed, this narrowing does not cover resolver mode's CI execution, and the
resolver's first live run waits.

## Deviations from the phase-2 plan in this build

- **E2 pointer variables retired.** The plan kept `OPENHANDS_SERVER_ENV` and
  `OPENHANDS_HEADERS`. The build derives both key-file paths from the validated run id and arm,
  so neither a caller's environment nor `status.json` can redirect them.
- **`OPENHANDS_COMPRESSION` added to the container environment.** The plan's closed list omits
  it. The request serializer and the server's preload need the same arm selection the host
  checked. The value is a recorded combo name or empty, and the proxy overwrites the header in
  any case.
- **`host.py teardown` added.** It is not a plan item. It removes a prepared attempt after a
  probe-only acceptance run and retries unconfirmed removals. It refuses while a conversation may
  be live.
- **Plan gate G7's P3 half is enforced through a recorded file (repair R6).** P3 is a live model
  call written as documented steps and a skeleton, and it has not run. The dispatch gate reads the
  coordinator's `stage-gates.json` record of it rather than observing P3 itself. The same file
  carries G2 and G5, and the engines-on arm's P4 and P5.

## Portable alias-refusal fixture repair (2026-10-03)

The custody repair serves the research-worker qualification step: exercise the resolver's
existing path-refusal policy on both Linux and macOS before any separately gated live run.
At PR head `501bcc9e`, the historical macOS full-suite artifact from run `36524134513`,
job `109263298833`, artifact `11015337319` reports three failures in
`PatchValidatorTests.test_case_unicode_and_filesystem_aliases_are_refused`: `docs/A.md`,
`Docs/z.md` and the NFD spelling of `docs/café.md`. The fixture wrote these through the
filesystem and exported them with `git add -A`; filesystem aliases and Git's filename
normalization can remove the intended spellings before the validator sees the patch.
`GitTree` instead reads the base with `ls-tree` and `cat-file`, and the refusal policy
compares the patch's names with the base's casefold/NFD keys.

**Chosen:** construct all seven test entries directly in the scratch repository's index,
following git/git `v2.43.0` `t/t2107-update-index-basic.sh:59-69`: write each blob with
`git hash-object -w --stdin`, then use `git update-index --add --cacheinfo
100644,<oid>,<path>`. Export the cached diff without restaging the worktree, and assert
that every intended path reached the validator. Keep every case, Unicode, trailing-dot,
NTFS-short-name, NTFS-stream and HFS-ignorable-character refusal assertion.

**Source-completeness finding:** index plumbing alone still allows Git's macOS argument
normalization. `git.c:449` calls `precompose_argv_prefix`, and
`compat/precompose_utf8.c:67-105` converts arguments when `core.precomposeUnicode` is true.
The test therefore passes `-c core.precomposeunicode=false` only to its scratch-index
insertion commands. This follows `Documentation/config/core.txt:44-51` and preserves the
decomposed name without changing repository configuration or the production validator.

**Alternatives:** a filesystem-prerequisite skip would leave these refusal checks unexercised
on the failing host; the maintained Git plumbing makes that fallback unnecessary. A blanket
platform skip would hide the regression and is not used. Worktree writes remain the default
for the other fixtures, which exercise the actual dispatch export path.

**Evidence and limits:** the original regression passes on Linux. Remapping only its three
alias writes to their canonical spellings reproduces the same three failures with the
existing unittest oracle; the repaired fixture passes that same synthetic check and all
11 patch-validator tests with real local Git 2.43.0. This is local integration and synthetic
evidence, not a new macOS run or upstream Git acceptance. Native macOS acceptance still
requires the pushed head's `validate-macos` full-suite artifact. The production refusal
gates and the proposed resolver-mode amendment above are unchanged.

**Overturn:** if a native macOS run on the repaired head still loses an intended spelling,
inspect that installed Git revision's argument/index handling and adjust the fixture from
its versioned primary sources. Do not weaken or skip the validator's refusal assertions.
