## Question and arms

Does GPT-6 at max effort beat the gateway's default medium effort for framework (FW) chat/completions roles by
enough to pay for its reasoning tokens?

| Arm | Model | Effort |
| --- | --- | --- |
| A | `cx/gpt-6-astra` | no `reasoning_effort` sent; the gateway default, medium per the gateway owner's measurement (PR #423) |
| B | `cx/gpt-6-astra-max` | max, from the built-in `-max` suffix alias (OmniRoute@dd6e9607e:open-sse/executors/codex.ts:1424-1431) |

Prompts, schema, headers and call order are identical apart from the model and the arm prefix in the two keys.
This is the li26 part of R02. Memory-role effort is decided on the S3 r6 development runs, not here.

## Request and headers

promptfoo 0.123.1's HTTP provider (`id: http`), one provider per arm, `maxRetries: 0` (the default is 4 silent
retries, site/docs/providers/http.md:1699, 1814). The configs are generated by `build_r02.py configs`.

- `POST http://127.0.0.1:20128/v1/chat/completions`, no `Authorization` header (keyless loopback gateway, the
  user's decision). Port 20129 runs the compression engines and would confound the arms.
- Body: `model`; one user message holding li26's prompt with the filing; `stream: true`;
  `stream_options: {include_usage: true}`; `response_format` with a strict `json_schema` derived at build time
  from the tiering run's `response.schema.json` (its per-filing object without `accession`,
  `additionalProperties: false`, the 34-code item enum). Never `json_object`.
- Headers, rendered with Nunjucks over each step's vars in `getHeaders` (promptfoo@0.123.1:src/providers/http.ts:2394,
  2409), which carry the evaluator's `__evalId`, `__evalStepId` and `__repeatIndex` (src/evaluator.ts:744-763,
  1646-1653):
  - `x-omniroute-session: r02-<a|b>-{{accession}}-r{{__repeatIndex}}-{{__evalId}}`, one per conversation;
  - `Idempotency-Key: r02-<a|b>-{{__evalId}}-{{__evalStepId}}`, one per call;
  - `X-Correlation-Id`, the same value as `Idempotency-Key` (59 characters on the wire). The gateway trims a caller
    id, removes CR and LF and keeps it when it is 1-256 characters long, otherwise it generates one
    (OmniRoute@dd6e9607e:src/app/api/v1/chat/completions/route.ts:292-298, 322;
    src/shared/utils/correlationPreserve.ts:6-12). It becomes the request id (src/sse/handlers/chat.ts:436), which
    call_logs stores as `correlation_id` with one row per gateway attempt
    (open-sse/handlers/chatCore/attemptLogging.ts:549-557, 611; src/lib/usage/callLogs.ts:713, 786, 801), and it
    is returned as the response header (src/sse/handlers/chatHelpers.ts:1172-1187; slow path route.ts:313-314);
  - `X-OmniRoute-No-Cache: true`.
- No sampling field in either arm: no `temperature`, `top_p`, `seed` or `max_tokens`, and no `reasoning_effort`.
  The gateway strips the first three for codex (OmniRoute@dd6e9607e:open-sse/translator/paramSupport.ts:48;
  open-sse/executors/codex.ts:1550-1573; the chat-to-Responses translation carries no seed,
  open-sse/translator/request/openai-responses/toResponses.ts:109-113, 432-453) and deletes `max_tokens`
  (codex.ts:1490-1494), which would also cap reasoning plus output. li26's `top_k`, `cache_prompt` and
  `chat_template_kwargs` are llama.cpp-only. Every field and its reason is in `plan.json` `request.not_sent`.
- With one user message and no tools, the gateway does not add its default Codex tool instructions (about 2,515
  tokens, per the gateway owner), because the full instructions are kept only for tool-capable requests
  (OmniRoute@dd6e9607e:open-sse/executors/codex.ts:1370-1378).
- The strict schema reaches the upstream as Responses `text.format` with `strict` kept
  (OmniRoute@dd6e9607e:open-sse/translator/request/openai-responses/toResponses.ts:35-56), and `text` passes the
  codex executor's field allowlist (codex.ts:1550-1573).
- The prompt function (`prompt_r02.py`) builds the text with li26's own `eval_arm.prompt_template(eval_arm.load_plan())`
  and `MARKER`, and refuses to return a prompt whose sha256 differs from the one recorded for that filing. The
  assertion (`assert_r02.py`) scores with li26's `eval_arm.parse_items` and `analyze.filing_scores`. The second
  assertion is promptfoo's own `is-json` with the exact schema the request sends, at its default weight (see
  Metrics).
- The transform (`transform_r02.js`) parses the SSE stream: output from `choices[0].delta.content`; usage from the
  last chunk that carries it, whatever its choices; the model, finish_reason, raw usage and the gateway's
  `X-Correlation-Id` go into metadata. So do the rate-limit-class response headers (names containing `ratelimit`
  or `rate-limit`) and the gateway's `X-OmniRoute-Dropped-Upstream-Headers`, for open question 3. promptfoo would
  otherwise keep none of them: the transform's metadata replaces the provider's `metadata.http`
  (promptfoo@0.123.1:dist/src/providers-BUaNtf-O.js:12936-12941, 13132-13136), and results redact `x-ratelimit-*`
  there (dist/src/evalResult-yO_CeNru.js:616-642). Failures are returned as errors with metadata rather than
  thrown, so a failed call keeps what the gateway returned.

## Metrics

Per arm, from the paired calls:

- **micro-F1** from TP/FP/FN summed per filing over repeats and then over filings, never an average of filing F1;
- **strict-schema validity**: the share of calls whose output passes promptfoo's `is-json` assertion with the
  exact schema sent in `response_format`: `JSON.parse` of the whole output, then ajv against the schema, the item
  enum and `additionalProperties` included (promptfoo@0.123.1 dist/src/evaluator-DlYW7Rgb.js:2509-2545). The
  analysis reads its `pass` per row from `gradingResult.componentResults` and requires its schema to hash to
  `plan.json` `request.schema_sha256`. The assertion keeps the default weight, because at weight 0 promptfoo
  reports `pass: true` whatever the check found (:5790-5793). li26's parse status (`valid`, `fenced_valid`,
  `invalid`) stays the scoring rule and is reported beside it: li26 accepts any unique code shaped like `9.99`,
  which the schema's enum rejects;
- **cost per filing**, per arm and usage field (reasoning, visible output = completion minus reasoning,
  completion = reasoning plus output, prompt, cached and uncached input), from the provider's own usage fields,
  not promptfoo's `tokenUsage.cached`. The estimand is paired per filing: each arm's mean over the filing's repeats,
  then the mean over the 60 filings. It is supported only when every call in both arms returned usage; otherwise it
  is reported as unsupported with the calls without usage per arm, and per-call means over the calls with usage
  are description only. The gateway writes `completion_tokens_details` and `prompt_tokens_details` only when their
  counts are above 0 (OmniRoute@dd6e9607e:open-sse/translator/response/openai-responses.ts:1403-1419), so on a
  call that returned usage an absent detail counts as 0; the analysis also reports how many calls carried each
  detail;
- **time to response headers** p50 and p95, over the calls that reached the transform. promptfoo's `latencyMs` for
  this provider stops before the body is read (dist/src/cache-CwCWVUtJ.js:422-432, 535-545;
  dist/src/providers-BUaNtf-O.js:12932-12934; dist/src/evaluator-DlYW7Rgb.js:7836), so it is not the call's
  duration, which is not recorded. A thrown provider error keeps 0 (:8036, 8075, 8150) and a deadline row the
  deadline (:8893), so neither is counted;
- **timeouts** per arm, split: `headers`, calls that failed with `Request timed out after <ms> ms`
  (`REQUEST_TIMEOUT_MS`, dist/src/fetch-DpK1Rb6J.js:1183), and `call_deadline`, calls that failed with `Evaluation
  timed out after <ms>ms` (`PROMPTFOO_EVAL_TIMEOUT_MS`, dist/src/evaluator-DlYW7Rgb.js:8888). A timed-out call stays
  in its arm as a failure, scored as returning nothing and without usage; it is never dropped or rerun (see Run
  commands). A timeout that names another value than the run environment's is an integrity problem;
- **429s**, on both sides of each call. A 429 that reaches promptfoo as an HTTP status is thrown before the
  transform and counted from the error text (promptfoo@0.123.1:src/util/fetch/index.ts:681-714, 768-770). A
  failure after the gateway has committed a slow-path 200 stream arrives as an in-band error chunk
  (OmniRoute@dd6e9607e:open-sse/utils/earlyStreamKeepalive.ts:664-685), so only call_logs shows whether it was a
  429. Every call's sent correlation id is rebuilt (see Correlation ids and call_logs), so both kinds join their
  call_logs rows. Per arm the analysis reports client-side 429 errors, observed 429 rows over all observed attempts
  and observed terminal rows with status 429, and cross-tabulates each call's client-side outcome with its observed
  terminal call_logs status. The call_logs figures are of an observed snapshot and so are lower bounds;
- **rate-limit headers**: per arm, the calls whose response carried a rate-limit-class header and the names seen,
  and the calls carrying the gateway's dropped-header count;
- other errors by kind.

- **Secondary, where non-NULL:** call_logs `reasoning_effort_requested` and `reasoning_effort_upstream` of each

  the response carried encrypted reasoning (OmniRoute@dd6e9607e:src/lib/usage/callLogs.ts:646-653), so a NULL is
  no observation, never "no effort". The script's six-column allowlist is unchanged, and request bodies stay
  off-limits.

## Correlation ids and call_logs

- **Sent ids, rebuilt.** promptfoo renders `__evalStepId` as `test-<testIdx>-prompt-<promptIdx>-repeat-<repeatIndex>`
  (promptfoo@0.123.1:dist/src/evaluator-DlYW7Rgb.js:7599-7605) and drops these runtime vars from the persisted
  vars (:7606-7619). Every result row still keeps `testIdx` and `promptIdx`, including a provider error thrown
  before the transform (:8087-8100, 8133-8157) and a step that hit the deadline (:8875-8898), and the results file
  keeps `evalId`. `testIdx` advances once per test and repeat, a test's repeats take consecutive values, and the
  providers of one step take `promptIdx` 0 and 1 in config order (:8612-8643, the repeat loop at :8622). So under
  the frozen schedule the filing of `testIdx` t is the run's roster entry t // 3, the repeat is t % 3, and the arm of
  `promptIdx` p is the run's provider order. `analyze_r02.py ids` rebuilds the sent id of every call from these
  fields. It refuses to continue when the results or tests files do not match the frozen schedule, or when an id
  the gateway echoed differs from the rebuilt one, since call_logs would then be joined on wrong ids. The echo
  check confirmed the rebuild for all 16 echoed calls.
- **Frozen schedule.** Before scoring or exporting ids, each results file must hold every (`testIdx`, `promptIdx`)
  cell of the 90 x 2 grid exactly once and nothing else, with the arm's provider label, the frozen filing and the
  tests file's labels, and must record the frozen promptfoo and Node versions. Each private tests file must match
  its frozen sha256 and hold the frozen roster in order. A timed-out step keeps its cell, and its late rows are
  skipped (:9137, 9216).
- **What promptfoo persists.** A row of `-o results.json` is `EvalResult.toEvaluateResult`
  (dist/src/eval-CUIvWaK2.js:1576-1597), whose vars are the test case's after promptfoo's secret sanitizer
  (dist/src/evalResult-yO_CeNru.js:609-615, 845, 1079). The sanitizer redacts the 64-hex `prompt_sha256`
  (dist/src/logger-ChlKG5Wv.js:718-730) and re-serializes a string that parses as JSON, so `labels_json` comes back
  compact (:1049-1057) and is compared as parsed JSON. The response, output and `metadata.r02` included, gets a JSON
  round trip and header redaction under `metadata.http` only (dist/src/evalResult-yO_CeNru.js:581-597, 626-681). A
  field the analysis reads that holds `[REDACTED]` is an integrity problem. The offline tests pass synthetic rows
  through the installed promptfoo's own `EvalResult` and analyze what it writes.
- **Several rows per id (open question 2).** The gateway writes one call_logs row per attempt under the same
  correlation id (OmniRoute@dd6e9607e:open-sse/handlers/chatCore/attemptLogging.ts:549-557, 611). It starts each
  attempt's save without awaiting it (:557-618), stamps the row after awaited lookups (src/lib/usage/callLogs.ts:
  538, 597, 602, 680) and inserts it only after an awaited artifact write (:759, 824). Neither the timestamp nor
  the insertion order therefore shows which attempt came last, and neither is used. The coordinator relayed an
  observation on :20128 from 2026-09-27: one id had a 503 row and a 200 row, and no 429 rows were seen. It was not
  reproduced here.
- **Terminal row.** Only the rows the snapshot observed count (see Observed snapshot). The client's own outcome
  decides:
  - a call promptfoo graded received a complete stream and must have an observed 2xx row;
  - a call whose HTTP status the client saw (the transform's `http_status_<code>`, a thrown 429) narrows to
    observed rows with that status and must have one;
  - for a transform stream error, a `rate_limit_header` failure, a timeout or another thrown error, all of the
    call's observed rows are candidates, because a slow-path stream commits 200 before the gateway's attempts end
    and then frames their error in-band (OmniRoute@dd6e9607e:open-sse/utils/earlyStreamKeepalive.ts:664-685).

  The observed terminal row is taken only when the candidates agree on status, model and both effort columns. It
  is the terminal row as far as the saved rows show; an attempt whose row was never saved could differ. A missing
  required row or disagreeing candidates make the terminal status unknown, an integrity problem, and a required row
  saved late or never looks the same, so it also voids the run. Rows per call, calls with several rows and 429
  rows count all observed rows. Several rows for one id are gateway attempts, never separate calls: with
  `maxRetries: 0` promptfoo sends one request per result row.
- **Observed snapshot.** call_logs is read as what it held at the reads, not as a complete log. After both runs,
  `call_logs_by_correlation.py` reads the ids' rows, waits 30 s and reads again until two consecutive reads are
  equal, for at most 600 s, and exits 3 if they never are; `analyze_r02.py` requires a settled snapshot with an
  interval of at least 30 s. Settling is a heuristic for saves still in flight, not a completeness check:
  - a save can land after the last read. The gateway starts it without awaiting it
    (open-sse/handlers/chatCore/attemptLogging.ts:557-618), stamps the row after awaited lookups
    (src/lib/usage/callLogs.ts:538, 597, 602, 680) and inserts it only after an awaited artifact write (:759, 824),
    and nothing bounds those waits;
  - a save can never land: its error is swallowed (attemptLogging.ts:618), and a save is skipped while persistence
    to disk is off or saves are closing (callLogs.ts:867);
  - the gateway's own drain, `waitForCallLogSaves` (:878-896), runs in-process and, outside its tests, only from
    graceful shutdown (`closeCallLogSaves`, :898-910; src/lib/gracefulShutdown.ts:114, 129), so a reader of the
    shared running gateway cannot call it. Its 2 s shutdown budget and the 10 s its tests wait
    (tests/unit/call-log-save-drain.test.ts:39) bound no save latency.

  No snapshot can show a late or lost save. So every call_logs figure is of observed rows, and the analysis report
  says so in `call_logs.scope`: rows per call, calls with several rows, 429 rows and the effort columns are lower
  bounds or observed values, a call without an observed row may have rows saved late or never, and a terminal
  status is the observed one (`observed_terminal_status`). The fail-closed checks stay: a graded call or a status
  the client saw without its observed row voids the run, so a late or lost save can void a run but cannot change
  a verdict.
- **Unmatched calls.** A sent id with no observed call_logs row is counted per arm by the call's client-side
  outcome, never dropped, unless promptfoo graded the call, which is an integrity problem. Such calls include
  requests that the gateway rejects before its attempt logging (a peer rejection, or backpressure when
  `OMNI_MAX_CONCURRENT_CONNECTIONS` is set: src/sse/handlers/chat.ts:432-433, 439-442;
  src/sse/utils/backpressure.ts:25-67) and calls whose rows were saved late or never; the count cannot tell them
  apart. The rebuild was chosen over a lookup by the run's `evalId` prefix because,
  for a completed run, the rebuilt ids already cover every sent request. **Gap:** a run that stops before promptfoo
  writes `-o` has no results file to rebuild from, and the prefix lookup is not implemented.

## Decision rule

First, **invalid**: any integrity problem voids the run. These are the frozen schedule, tests files and promptfoo
and Node versions; li26 rescoring and the prompt check; the `is-json` schema; correlation echoes; the call_logs
snapshot and observed terminal rows; the timeouts' values; the analysis environment; and the gateway read-backs
and their admissible values.
`analyze_r02.py` then reports status and `decision.result` `invalid`, computes no statistic, writes `--out` and
exits 2. Otherwise, with the one-sided 95% bounds below:

- **adopt max** only if the lower bound of micro-F1(B) - micro-F1(A) is above 0; this does not depend on cost;
- otherwise **keep medium** if A is non-inferior (the lower bound of micro-F1(A) - micro-F1(B) is at least -0.02)
  and the cost leg is supported and shows A's completion (reasoning plus output) tokens per filing below B's;
- otherwise **inconclusive**: B is not adopted, and neither A's non-inferiority nor its cost advantage is shown.

The cost leg is the paired per-filing estimand for completion tokens (see Metrics), supported only when all 360
calls returned usage. Averaging only the calls that returned usage could reverse the comparison. With 59 filings
at 10 tokens in both arms and one filing at 1,000 tokens in A and 900 in B, losing one of A's 1,000-token calls
gives 21.06 against 24.83 per call, while per filing A costs 26.5 and B 24.83.

Report the cost per filing for both arms with the decision. Moving a role to `cx/gpt-6-sol` is outside these arms.

- `PROMPTFOO_EVAL_TIMEOUT_MS=1320000`, 22 minutes per eval step, is an independent experimental deadline
  (dist/src/logger-ChlKG5Wv.js:134-136). promptfoo races each step against it and, on expiry, aborts the call and
  records an error row `Evaluation timed out after <ms>ms` (dist/src/evaluator-DlYW7Rgb.js:9191-9230, 8875-8898).
  It clears the timer only when the step's rows are ready (:9125-9133), so everything from the step's start counts
  toward it: the gateway's queueing and account selection, every gateway attempt and retry, the wait for the
  upstream's response and reading the stream.
- The gateway's own limits start at different points and do not add up to a bound under the deadline. Its stream
  watchdogs are armed only when the streaming pipeline is built on an upstream response it already has
  (OmniRoute@dd6e9607e:open-sse/utils/streamHandler.ts:1135-1141; open-sse/handlers/chatCore.ts:6386), so
  pre-stream waiting and retries are outside them. A call within every gateway limit can therefore still reach the
  deadline.
- A call that reaches it is a failure of its arm: error kind `call_deadline`, scored as a call that returned
  nothing, without usage (so the cost leg becomes unsupported), and reported per arm. Max effort may reach it more
  often, which then counts against arm B. The value is not derived from measured durations, which were never
  recorded.
- `REQUEST_TIMEOUT_MS=660000` bounds only the wait for response headers: promptfoo clears its timer when they
  arrive (dist/src/fetch-DpK1Rb6J.js:1177-1195) and reads the body afterwards (dist/src/cache-CwCWVUtJ.js:422-432).
  It was chosen above the gateway's default upstream fetch timeout, 600,000 ms
  (OmniRoute@dd6e9607e:src/shared/utils/runtimeTimeouts.ts:9), but queueing, account selection and retries before
  the headers count toward it too, so it is no promise that the gateway answers first. A call that reaches it fails
  as `headers_timeout` of its arm.

The results do not record these variables (dist/src/evaluator-DlYW7Rgb.js:9193;
dist/src/logger-ChlKG5Wv.js:706-713), so a timeout shows only when it fires, and the analysis then requires the
frozen value in its error text. The `PROMPTFOO_STRIP_*` projections (dist/src/evalResult-yO_CeNru.js:784-791)
would remove what the analysis reads, `PROMPTFOO_SHORT_CIRCUIT_TEST_FAILURES` would drop the `is-json` result after

## Limitations

- The account behind each call is an uncontrolled factor: per-conversation session keys spread calls across the
  gateway's 4 accounts. No account column is read; the gateway owner supplies the masked per-arm distribution.
  - Account selection includes the OAuth occupancy override, which no setting disables at this pin. Every chat
    request asks for it (`reserveOAuthSession: true`, OmniRoute@dd6e9607e:src/sse/handlers/chat.ts:1711), and it
    moves a call to another OAuth connection of the same or next priority when that one has more session
    availability (src/sse/services/auth.ts:2159-2176).
  - The gateway owner measured its effect on 20128's multi-turn Codex traffic on 2026-09-28:
    - 10.3% of turns were served away from their pinned account;
    - those turns had a cache-read share of 73.8%, against 92.1% for pinned turns;
    - 25.8% of Codex turns switched account mid-turn and dropped `x-codex-turn-state`.

    These figures are relayed, not reproduced here.
  - R02's conversations are single calls, so no call has an earlier pinned account in its conversation. The
    override acts as part of account selection, and a mid-call switch shows as attempts on more than one account.
  - Both arms run through it, so it is a shared condition, not part of either treatment. It can move the cached
    input share and the time to response headers, which are descriptive metrics.
  - The owner's post-run report gives, per arm, the calls whose attempts were served by more than one account, so
    an uneven effect between the arms is visible.
- A call without an observed call_logs row, because the gateway rejected it before its attempt logging or because
  its rows were saved late or never, is counted as unmatched by client-side outcome (see Correlation ids and
  call_logs).
- promptfoo treats a 200 response that carries `x-ratelimit-remaining-requests`, `x-ratelimit-remaining-tokens` or
  `X-RateLimit-Remaining` equal to 0 as rate limited and, with `maxRetries: 0`, fails the call
  (promptfoo@0.123.1:src/util/fetch/index.ts:375-388, 712-714; installed dist/src/fetch-DpK1Rb6J.js:1200-1204,
  1432-1453, 1464-1495).
  - The gateway forwards rate-limit-class upstream headers on fast-path streams within its budget.
  - The re-check saw none on its 2 calls.
  - Such a failure is classified `rate_limit_header`, and call_logs still shows the gateway's side of the call
    through its rebuilt id.
- Other clients (hindsight-live, cognee-live) call `cx/gpt-6-astra-max` through the same gateway, which is why
  call_logs is read by correlation id and never by window and model.
- Integrity is strict: any failed check voids the whole run. That includes an error call whose call_logs rows
  disagree or lack the status the client saw, so if the gateway returns one status and logs another, every such
  call voids the run. Any call without usage makes the cost leg unsupported, so keep medium needs all 360 calls
  to return usage.
- The deadline and the header timeout are preregistered client bounds, not gateway guarantees: a call within every
  gateway limit can still reach them and then counts as a failure of its arm. They are not recorded in the
  results and show only when one fires. Neither is derived from measured durations.
- The gateway configuration is the owner's sanitized report, not an independent observation, checked against the
  declared admissible values. It covers the settings this plan traced, not every setting of the gateway. By the
  pinned source, arm A (no suffix, no effort in the body) runs at medium only when no rule sets its effort, the
  thinking-budget mode is PASSTHROUGH and the serving connection has no `reasoningEffort` default
  (OmniRoute@dd6e9607e:open-sse/executors/codex.ts:1275-1277, 1439-1441, 1451-1456); the admissible values require
  exactly that. In another mode its effort would come from the thinking-budget handling or the upstream's default,
  which this plan does not trace.
- `promptfoo_build` hashes the promptfoo package outside `node_modules`; its dependencies are not hashed.
- call_logs is an observed snapshot: a save that lands after the last read, or never lands, is not in it and
  cannot be detected. Row counts are lower bounds, a terminal status is the observed one, and a required row lost
  this way voids the run rather than changing a verdict.
