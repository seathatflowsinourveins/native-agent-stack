# Gateway A/B R02: FW effort, medium versus max, on li26 through OmniRoute

**Status: DRAFT, not frozen, not run.** Built 2026-09-27. Only the bounded wire check has run (2 gateway calls,
below). No scored call has been made, and the wire check does not freeze the design. Before the first scored call
the plan is frozen with its hashes and gets the GPT-6 review the design requires.

Machine-readable plan: [plan.json](plan.json). Offline checks: `tests/test_gateway_ab_r02_20260927.py`.

## Question and arms

Does GPT-6 at max effort beat the gateway's default medium effort for framework (FW) chat/completions roles by
enough to pay for its reasoning tokens?

| Arm | Model | Effort |
| --- | --- | --- |
| A | `cx/gpt-6-astra` | no `reasoning_effort` sent; the gateway default, medium per the gateway owner's measurement (PR #423) |
| B | `cx/gpt-6-astra-max` | max, selected by the model alias |

Prompts, schema, headers and call order are identical apart from the model and the arm prefix in the two keys.
This is the li26 part of R02. Memory-role effort is decided on the S3 r6 development runs, not here.

## Request and headers

promptfoo 0.123.1's HTTP provider (`id: http`), one provider per arm, `maxRetries: 0` (the default is 4 silent
retries, site/docs/providers/http.md:1699, 1814). The configs are generated by `build_r02.py configs`.

- `POST http://127.0.0.1:20128/v1/chat/completions`, no `Authorization` header (keyless loopback gateway, the
  user's decision). Port 20129 runs the compression engines and would confound the arms.
- Body: `model`; one user message holding li26's prompt with the filing; `stream: true`;
  `stream_options: {include_usage: true}`; `response_format` with a strict `json_schema` derived at build time
  from the tiering run's `response.schema.json` (its per-filing object without `accession`,
  `additionalProperties: false`, the 34-code item enum). Never `json_object`.
- Headers, rendered with Nunjucks over each step's vars in `getHeaders` (promptfoo@0.123.1:src/providers/http.ts:2394,
  2409), which carry the evaluator's `__evalId`, `__evalStepId` and `__repeatIndex` (src/evaluator.ts:744-763,
  1646-1653):
  - `x-omniroute-session: r02-<a|b>-{{accession}}-r{{__repeatIndex}}-{{__evalId}}`, one per conversation;
  - `Idempotency-Key: r02-<a|b>-{{__evalId}}-{{__evalStepId}}`, one per call;
  - `X-OmniRoute-No-Cache: true`.
- No sampling field in either arm: no `temperature`, `top_p`, `seed` or `max_tokens`, and no `reasoning_effort`.
  The gateway strips the first three for codex (OmniRoute@dd6e9607e:open-sse/translator/paramSupport.ts:48;
  open-sse/executors/codex.ts:1550-1573; the chat-to-Responses translation carries no seed,
  open-sse/translator/request/openai-responses/toResponses.ts:109-113, 432-453) and deletes `max_tokens`
  (codex.ts:1490-1494), which would also cap reasoning plus output. li26's `top_k`, `cache_prompt` and
  `chat_template_kwargs` are llama.cpp-only. Every field and its reason is in `plan.json` `request.not_sent`.
- With one user message and no tools, the gateway does not add its default Codex tool instructions (about 2,515
  tokens, per the gateway owner), because the full instructions are kept only for tool-capable requests
  (OmniRoute@dd6e9607e:open-sse/executors/codex.ts:1370-1378).
- The strict schema reaches the upstream as Responses `text.format` with `strict` kept
  (OmniRoute@dd6e9607e:open-sse/translator/request/openai-responses/toResponses.ts:35-56), and `text` passes the
  codex executor's field allowlist (codex.ts:1550-1573).
- The prompt function (`prompt_r02.py`) builds the text with li26's own `eval_arm.prompt_template(eval_arm.load_plan())`
  and `MARKER`, and refuses to return a prompt whose sha256 differs from the one recorded for that filing. The
  assertion (`assert_r02.py`) scores with li26's `eval_arm.parse_items` and `analyze.filing_scores`.
- The transform (`transform_r02.js`) parses the SSE stream: output from `choices[0].delta.content`; usage from the
  last chunk that carries it, whatever its choices; the model, finish_reason, raw usage and the gateway's
  `X-Correlation-Id` go into metadata. Failures are returned as errors with metadata rather than thrown, so a
  failed call keeps its correlation id.

## Metrics

Per arm, from the paired calls:

- **micro-F1** from TP/FP/FN summed per filing over repeats and then over filings, never an average of filing F1;
- **strict-schema validity**: the share of calls li26's `parse_items` marks `valid` (`fenced_valid` is scored but
  is not strict-schema valid);
- **cost per filing** (one call processes one filing once, so the mean per call): reasoning tokens, visible output
  (completion minus reasoning), completion (reasoning plus output), prompt, uncached input and the cached-input
  share, from the provider's own usage fields, not promptfoo's `tokenUsage.cached`. The gateway writes
  `completion_tokens_details` and `prompt_tokens_details` only when their counts are above 0
  (OmniRoute@dd6e9607e:open-sse/translator/response/openai-responses.ts:1403-1419), so on a call that returned
  usage an absent detail counts as 0; the analysis also reports how many calls carried each detail;
- **latency** p50 and p95 (promptfoo `latencyMs`);
- **timeouts** (promptfoo's `Request timed out after <ms> ms`, `REQUEST_TIMEOUT_MS` 300000);
- **429s**, as two partial counts side by side. A 429 that reaches promptfoo as an HTTP status is thrown before the
  transform, so it is counted from the error text and carries no correlation id
  (promptfoo@0.123.1:src/util/fetch/index.ts:681-714, 768-770). A failure after the gateway has committed a
  slow-path 200 stream arrives as an in-band error chunk (OmniRoute@dd6e9607e:open-sse/utils/earlyStreamKeepalive.ts:664-685),
  which keeps its correlation id, so only call_logs shows whether it was a 429. Neither count alone is complete
  (open question 1);
- other errors by kind.

## Effective effort

- **Primary:** the client-observed `usage.completion_tokens_details.reasoning_tokens` per call, attributable by
  correlation id. Per filing the mean over repeats; B minus A with the same paired filing bootstrap and samples
  permutation test as quality. **Second view:** `completion_tokens`. The analysis also reports each arm's mean,
  median, p95 and zero share.
- About 14% of max-effort turns return 0 reasoning tokens as model behaviour (token-save-practice-gpt6's
  measurement, relayed by the coordinator on 2026-09-27; not measured here), so a per-call zero is not a defect.
  The arms are compared by distribution.
- **Secondary, where non-NULL:** call_logs `reasoning_effort_requested` and `reasoning_effort_upstream`, read by
  correlation id with `call_logs_by_correlation.py`. They are filled only when the response carried encrypted
  reasoning (OmniRoute@dd6e9607e:src/lib/usage/callLogs.ts:646-653), so a NULL is no observation, never "no
  effort". The script's six-column allowlist is unchanged, and request bodies stay off-limits.

## Decision rule

With the one-sided 95% bounds below:

- **adopt max** only if the lower bound of micro-F1(B) - micro-F1(A) is above 0;
- otherwise **keep medium** if A is non-inferior (the lower bound of micro-F1(A) - micro-F1(B) is at least -0.02)
  and A's mean completion (reasoning plus output) tokens per filing are below B's;
- otherwise **inconclusive**: B is not adopted, and neither A's non-inferiority nor its cost advantage is shown.

Report the cost per filing for both arms with the decision. Moving a role to `cx/gpt-6-sol` is outside these arms.

## Statistics

- Pairing by (accession, repeat): promptfoo gives both arms of a filing and repeat the same `testIdx`
  (src/evaluator.ts:2674-2696). The unit is the filing, with TP/FP/FN summed over its repeats.
- `scipy.stats.bootstrap` (scipy 1.18.1, scipy/stats/_resampling.py:300): `paired=True`, `vectorized=True`,
  `method="percentile"`, `n_resamples=10000`, `confidence_level=0.95`, `alternative="greater"` (the lower end is
  the 5th percentile, :651-683), `rng=numpy.random.default_rng(20260927)`. Each filing's two arms are rows of one
  count table and the samples carry row indices, so a resample moves both arms of a filing together.
- `scipy.stats.permutation_test(permutation_type="samples")` (:1679), same seed, as the secondary check.
- Holm through statsmodels 0.15.0 `multipletests(method="holm")` (statsmodels/stats/multitest.py:99) applies only
  to a family of roles. R02 compares one role, so it is not applied.
- li26's own `paired_bootstrap` is not reused.

## Run commands (after freezing)

From the repository root:

```sh
BP=blueprints/convergence-practice/gateway-ab-r02-20260927
STATE=~/.local/state/native-agent-stack/gateway-ab-r02-20260927
ACQ=~/.local/state/native-agent-stack/local-inference-latest-20260926/sec/acq-20260926
python3 $BP/build_r02.py subset --acquisition $ACQ --state-dir $STATE --check
python3 $BP/build_r02.py configs --check
python3 $BP/build_r02.py frozen --check

export PROMPTFOO_CONFIG_DIR=$STATE/promptfoo PROMPTFOO_DISABLE_TELEMETRY=1 REQUEST_TIMEOUT_MS=300000
RUN=$STATE/run-1; mkdir -m 700 $RUN
date -u +%Y-%m-%dT%H:%M:%S.%3NZ > $RUN/window.txt
promptfoo eval -c $BP/promptfooconfig.ab.json -t $STATE/tests-ab.jsonl --repeat 3 --max-concurrency 1 \
  --no-cache --no-share -o $RUN/results-ab.json
promptfoo eval -c $BP/promptfooconfig.ba.json -t $STATE/tests-ba.jsonl --repeat 3 --max-concurrency 1 \
  --no-cache --no-share -o $RUN/results-ba.json
date -u +%Y-%m-%dT%H:%M:%S.%3NZ >> $RUN/window.txt

python3 $BP/analyze_r02.py ids --results $RUN/results-ab.json $RUN/results-ba.json > $RUN/ids.json
python3 $BP/call_logs_by_correlation.py ~/.local/share/omniroute/storage.sqlite $RUN/ids.json --rows \
  > $RUN/call-logs.json
uv run --with scipy==1.18.1 --with statsmodels==0.15.0 --with numpy python $BP/analyze_r02.py analyze \
  --results-ab $RUN/results-ab.json --results-ba $RUN/results-ba.json --call-logs $RUN/call-logs.json \
  --repeats 3 --out $RUN/decision.json
chmod 600 $RUN/*
```

`--no-cache` turns off promptfoo's own response cache; `X-OmniRoute-No-Cache: true` is the gateway's, so both are
set. The run makes 360 calls (60 filings, 3 repeats, 2 arms). Results, ids and call_logs output hold filings and
correlation ids: keep them in the private state directory and publish only a sanitized decision receipt.

## Limitations

- The account behind each call is an uncontrolled factor: per-conversation session keys spread calls across the
  gateway's 4 accounts. No account column is read; the gateway owner supplies the masked per-arm distribution.
- 429s are only partly attributable (see Metrics).
- promptfoo treats a 200 response that carries `x-ratelimit-remaining-requests`, `x-ratelimit-remaining-tokens` or
  `X-RateLimit-Remaining` equal to 0 as rate limited and, with `maxRetries: 0`, fails the call
  (promptfoo@0.123.1:src/util/fetch/index.ts:375-388, 712-714). Whether the gateway forwards such headers is unknown.
- Other clients (hindsight-live, cognee-live) call `cx/gpt-6-astra-max` through the same gateway, which is why
  call_logs is read by correlation id and never by window and model.

## Deviations from the brief

- Wire check (a) hit its stop condition (above); it was reported, not worked around.
- The gateway owner's changes relayed on 2026-09-27 replace brief points 4 and 6 and the effort read: no sampling
  field in either arm, usage from the last usage-bearing chunk, call_logs read by correlation id with its own
  read-only script, and an added wire check (e). The coordinator's effort note replaces "effort from call_logs"
  with reasoning tokens as the primary measure.
- The transform returns `{error, metadata}` instead of throwing, because a thrown error loses the metadata that
  carries the correlation id (promptfoo@0.123.1:src/evaluator.ts:1212-1271 versus 1799-1830).
- Header rendering is cited at http.ts:2394 and 2409 (the brief's 2249-2253 render `sessionConfig`).
- `__evalStepId` includes the prompt column index (`test-<i>-prompt-<j>-repeat-<k>`, src/evaluator.ts:759), which
  differs between the providers; the arm prefix still guarantees distinct keys.
- Offline tests use `unittest.skipUnless` rather than `pytest.importorskip`, following the repository's test
  convention (`python3 -m unittest` in CI); pytest runs them unchanged.
- Labels travel as a JSON string var (`labels_json`), because promptfoo expands a list-of-strings var into one test
  per value (src/evaluator.ts:1941-1975).

## Decision record (2026-09-27)

promptfoo 0.123.1's HTTP provider with the glue in this directory. Alternatives:

- **promptfoo `openai:chat` with session hooks** (the reviewed design's first choice). Its headers pass through
  unrendered (promptfoo@0.123.1:src/providers/openai/chat.ts:479) and only `reasoning_effort` is rendered from test
  vars (chat.ts:225, 303), so per-conversation session keys and per-call idempotency keys would need hooks around
  every call. Overturned by a promptfoo release whose `openai:chat` renders header templates per call, which would
  also replace `transform_r02.js` with promptfoo's own usage mapping.
- **A self-written runner.** Excluded by the user's direction to use upstream harnesses for E2E and A/B tests.
  Overturned only by a promptfoo defect that blocks a required control with no upstream fix.
- **Inspect** (inspect_ai 0.3.271, the runner-up in the session's eval-framework comparison). Not used: promptfoo
  is the catalog's pinned evaluation harness (`manifests/stack.json`) and runs li26's scorer unchanged as a Python
  assertion. Overturned by a matched comparison in which Inspect carries per-call headers, streamed usage and
  li26's scorer with less glue or better per-call evidence, for example for the client-side 429s promptfoo cannot
  attribute.

## Open questions for the gateway owner

1. The pinned gateway keeps a caller-provided `X-Correlation-Id` (1-256 characters) as the request id
   (OmniRoute@dd6e9607e:src/app/api/v1/chat/completions/route.ts:292-298; src/shared/utils/correlationPreserve.ts:6-12),
   which becomes `call_logs.correlation_id` (src/sse/handlers/chat.ts:436; src/lib/usage/callLogs.ts:713, 786, 801).
   Sending `X-Correlation-Id: r02-<a|b>-{{__evalId}}-{{__evalStepId}}` (about 60 characters) would make every call
   joinable, including client-side 429s and timeouts, whose ids the analysis could rebuild from `evalId`, `testIdx`,
   the prompt column and the repeat. Should R02 send it? It changes the approved request shape and would need a
   2-call wire re-run; it is not added.
2. Does the gateway retry an upstream 429 on another account, and does each attempt get its own call_logs row
   under the same correlation id?
3. Does the gateway forward `x-ratelimit-remaining-*` or `X-RateLimit-Remaining` headers on a 200 (see Limitations)?
4. Is there an observation of arm A's effective effort that does not depend on encrypted reasoning, besides PR #423?
