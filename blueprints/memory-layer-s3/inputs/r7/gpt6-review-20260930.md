### F1 [high] PREREGISTRATION.md §§1, 8.4; maintenance gate
- Issue: Calling Harbor task bundles hashed data does not prevent execution of code from the stale harbor-datasets repository. The design cannot currently substantiate its universal no-stale-code claim.
- Evidence: PREREGISTRATION.md:65 prohibits “scripts, evaluators, prompt code or packages built from it,” but :583 permits tasks “only as hashed data.” The permitted pinned repository contains executable task tests, for example “python /tests/llm_judge.py” in [harbor-datasets@37db1088, tests/test.sh:4](https://github.com/harbor-framework/harbor-datasets/blob/37db108843a49bb31a592e37a75e2c40dc3f9749/datasets/aa-lcr/aa-lcr-1/tests/test.sh#L4). The active [Harbor verifier@1e5c5c6d:175–232](https://github.com/harbor-framework/harbor/blob/1e5c5c6db929a10a140d05e606882c671ae20729/src/harbor/verifier/verifier.py#L175-L232) uploads task tests and executes their command. No selected-task manifest establishes that such code is excluded.
- Fix: Freeze a task-level provenance manifest distinguishing inert inputs from Dockerfiles, setup scripts, tests and judges. Permit execution only from gate-passing sources, with explicit enforcement. Replace the executable task components through maintained upstream sources or leave the Harbor lane pending.

### F2 [high] PREREGISTRATION.md §§2, 4.3–4.5; Hindsight parity
- Issue: The reused vendor provider silently changes Hindsight's native pipeline. Judge-free scoring and an audit promise do not resolve this concrete configuration mismatch.
- Evidence: PREREGISTRATION.md:254 promises providers operate “without changing ingest or recall semantics,” and :256 selects hindsight-http. Its inherited [bank configuration@03c1d0f1:218–243](https://github.com/vectorize-io/agent-memory-benchmark/blob/03c1d0f1d27da63034f0931121c858faba512383/src/memory_bench/memory/hindsight.py#L218-L243) sets “kwargs: dict = dict(enable_observations=False)”; the asynchronous bank-creation path also uses these kwargs (:425–433). Hindsight's pinned [native configuration@5fc4ce20:1711–1712](https://github.com/vectorize-io/hindsight/blob/5fc4ce20917b916240cef27c212c387a177f115b/hindsight-api-slim/hindsight_api/config.py#L1711-L1712) defaults observations and automatic consolidation to True. This changes retrieval, ingest work and cost. Additionally, the provider's asynchronous recall ignores k and uses token budgets, so the draft's “equal candidate depth” requirement (:284) needs an operational definition.
- Fix: Preserve the selected native bank configuration through supported configuration or a thin local provider, keeping AMB unchanged. Freeze and verify effective bank settings before ingestion. Resolve every provider's depth policy and test the actual asynchronous ingest/recall paths, including failure handling, in the parity audit.

### F3 [high] PREREGISTRATION.md §7.2; winner and tie-break set
- Issue: Membership in the tie-break set is undefined when several systems share the highest point estimate. This can change the selected system.
- Evidence: PREREGISTRATION.md:463 defines L as “on an exact tie, every tied system,” but :464 uses the singular condition “whose Holm-adjusted test against L ... does not reject.” Equal point estimates need not produce equal paired-test results against a third system because their question-level differences can have different variances. A candidate within 0.02 could therefore be separated from one co-leader but not another.
- Fix: Define the maximizer set explicitly and specify the quantifier. For example, admit a non-maximizer only when it is within 0.02 and is not significantly worse than every co-leader. Freeze executable examples covering tied leaders with conflicting pairwise decisions, and multiple equal minimum costs.

### F4 [medium] PREREGISTRATION.md §§5.2, 7.3; decision record:84
- Issue: The cost scalar does not clearly distinguish gross priced usage from usage differences after subtracting the no-memory control. The distinction changes the 0.80 ratio and can produce zero or negative costs.
- Evidence: PREREGISTRATION.md:326 says “The same client's no-memory control on the same workload is subtracted pairwise.” At :334, C is “summed over every model invocation in ledgers (a) and (c).” Gross costs of 120 and 130 do not meet the 0.80 threshold; subtracting a common baseline of 100 produces 20 and 30, which do. Equal zero or negative minima also make the singular selection instruction at :473 ambiguous.
- Fix: Define C explicitly as nonnegative gross workload cost and report control-subtracted differences separately, or replace the ratio with a prespecified rule suitable for signed incremental costs. Specify equal-minimum handling and the corresponding RAG workload.

### F5 [medium] PREREGISTRATION.md §§5.3, 7.5; decision record:81
- Issue: The generalized fallback preflight combines incompatible concurrency requirements.
- Evidence: PREREGISTRATION.md:504 requires the preflight to run “at the confirmatory concurrency K and on 5.3's warm schedule,” while :349 freezes that schedule at “concurrency 1.” This matters for saturation-triggered fallbacks, including ai-memory's four-call cap.
- Fix: Specify separate measurements: fallback behavior under confirmatory load K, and gated warm latency at concurrency 1. State which workload and denominator determine the 5% fallback threshold and which result controls stage disabling.

### F6 [medium] PREREGISTRATION.md §7.4; decision record:85
- Issue: The pinned-commit CI term can award full credit while relevant jobs remain unfinished.
- Evidence: PREREGISTRATION.md:491 awards K=10 when “every completed check run” has an allowed conclusion and the combined status “is not failure or error.” One successful completed lint check plus an in-progress test run and pending combined status satisfies that wording.
- Fix: Require the frozen relevant check/status set to be complete, with no queued, in-progress or pending entries, before awarding K=10. Specify pagination and handling of missing or inconclusive results. Retain the explicit description of release cadence and its weights as coordinator heuristics.

### F7 [medium] PREREGISTRATION.md §7.1; decision record:83
- Issue: The symmetric usefulness floor establishes relative ranking but no minimum usefulness for deployment.
- Evidence: PREREGISTRATION.md:459 requires successes to be “at least the highest success count among the systems meeting items 1–5, minus one.” If all systems achieve 0/25, every otherwise qualifying system passes this floor; a zero-success system also passes when the best achieves 1/25.
- Fix: Add a common absolute usefulness requirement or a requirement relative to the same no-memory control, while retaining symmetry. Alternatively, obtain explicit acceptance that this is solely a relative filter and that selection provides no absolute usefulness qualification.
