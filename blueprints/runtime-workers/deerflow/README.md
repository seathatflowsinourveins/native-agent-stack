DeerFlow 2.1.0 is a **draft multi-agent runtime-worker recipe**, powered by GPT-6 through the local OmniRoute gateway. The deliverable is configuration, installation instructions, and a DeerFlow transport solver for the upstream GAIA benchmark. Source inspection and offline integration checks are evidence for this recipe; Docker startup, model calls, and runtime acceptance must be measured by the coordinator. No host installation, image pull, service start, production-service modification, or live E2E was performed while building it. This belongs to `lane:foundation`; the trading DeerFlow/codex-acp recipe is reference only.

The rootless Compose deployment publishes **only nginx, at `127.0.0.1:3771`**. Backend, frontend, nginx, and Redis startup scripts choose their container's private interface explicitly. There is no host-network mode and no Docker socket mount. Rootless Docker/Compose are prerequisites supplied separately, not installed by this recipe. Docker verifies content-addressed image layers; the installer also checks returned `RepoDigests` and the release image revision labels, saving private post-pull image metadata. It downloads the source archive only after defining its SHA256, checks both upstream lockfile hashes, and creates its prefix at `$HOME/.local/share/codex-ecosystem/tools/deerflow-2.1.0`. All writable application/MCP/cache/run state lives below `$HOME/.local/state/native-agent-stack/runtime-workers/deerflow`, with private directories mode 0700 and configuration files mode 0600. Shared MCP dependency mounts are read-only; QMD queries use an owned writable snapshot of the adopted index.

For code execution, the chosen provider is **upstream `deerflow.sandbox.local:LocalSandboxProvider` inside the gateway container**, with `sandbox.allow_host_bash: true`. Its paths are scoped per thread, but it is a trusted single-user worker: code and stdio MCP processes share the gateway container and can reach that worker's mounted data. It is not per-thread process isolation. [config.example.yaml:1436–1472](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/config.example.yaml#L1436-L1472) documents the setting and the container-relative mount requirement; [LocalSandboxProvider:36–70](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/backend/packages/harness/deerflow/sandbox/local/local_sandbox_provider.py#L36-L70) states its isolation limits.

Upstream's AIO provider would require controlling Docker from the backend through the opt-in [DooD overlay:1–26](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/docker/docker-compose.dood.yaml#L1-L26). **Private host preparation is necessary before running the installer.** Copy [host.json.example](host.json.example) to a mode-0600 file outside the checkout. Fill the Docker executable, adopted ecosystem root, actual local Qdrant/embedding endpoints, and narrow same-path mounts for the existing MCP binaries, their pinned tool prefixes, and interpreter targets, plus the source QMD database and its four collection definitions. Stdio programs run inside the backend image, so a host registration alone cannot make them available. Do not mount the whole home, ecosystem root, credential stores, Docker socket, or the recipe prefix. Executable symlinks must resolve inside the container; any external Python/Node interpreter target needs its own read-only mount. `qmd_snapshot` supplies an existing named index database and exactly those four collection definitions. The installer uses SQLite backup from a read-only source connection to create a consistent snapshot, including live WAL contents, under owned `/state/mcp/qmd`. It rejects other or empty collections, never indexes or refreshes the shared source, and preserves an existing snapshot on reinstall. The `.yml` configuration is JSON-compatible YAML containing only path/pattern definitions; update hooks and editor settings are omitted. Native QMD requires a writable database/cache even for queries, so the shared original is never used directly. Names and paths follow [QMD v2.8.3 collections.ts:101–125](https://github.com/tobi/qmd/blob/v2.8.3/src/collections.ts#L101-L125) and [store.ts:636–653](https://github.com/tobi/qmd/blob/v2.8.3/src/store.ts#L636-L653). Original source document paths need not be mounted for retained database retrieval. Snapshot refresh is a separate explicit host action. QMD inherits the adopted Node PATH to preserve the native-module ABI. Missing dependencies fail the preflight; the recipe does not invent a download command or mutate the adopted host installs to fix them.

[gaia.py](e2e/gaia.py) follows Inspect's [custom solver API](https://github.com/UKGovernmentBEIS/inspect_ai/blob/0.3.271/docs/solvers.qmd). It sends `state.input_text` unchanged through the native embedded DeerFlow client and sets `ModelOutput` to the returned answer. It never reads the target. [check.py](e2e/check.py) only rejects missing, malformed, failed or incomplete transport: it requires a native `end` event and a final assistant message in the last `values` snapshot. It preserves the answer text, including wrong answers, and never concatenates streamed deltas with complete snapshots. It executes no worker-generated code and gives no quality verdict. The previous release-diff task and expected output remain historical round-1 evidence only; [task.md](e2e/task.md) now defines the GAIA run contract.

At each run's start, [drive.py](e2e/drive.py) calls native [`DeerFlowClient.list_skills(enabled_only=True)`](https://github.com/bytedance/deer-flow/blob/v2.1.0/backend/packages/harness/deerflow/client.py#L1255-L1277) and records the exact returned names in `worker-skills`. Native GAIA input is not altered to force an activation claim. A GAIA score can exist with this skills gate still unmet; inspect both before accepting the worker. An interactive user's custom skills can shadow the legacy category and require rechecking.

**Structured calls follow the measured OmniRoute contract.** The pinned ChatOpenAI adapter selects upstream `with_structured_output(..., method="function_calling", strict=False)` and retains the upstream output parser, including `include_raw`. This uses tool calling, so it does not rely on a moved system message satisfying `json_object`, or on arbitrary schemas satisfying strict object rules. Direct raw `response_format` and Responses `text.format` JSON modes are rejected before network I/O. Mixed auxiliary tools plus structured output in one `with_structured_output` call are also rejected; ordinary `bind_tools` remains native. Server-enforced strict output schemas are not claimed. Nested strict-schema mode is not enabled.

Every generated model payload has a conversation-stable `x-omniroute-session`, a fresh UUID `Idempotency-Key` for a logical call, and no temperature. SDK retries reuse the already-built request payload. Embedded runs set `DEERFLOW_CONVERSATION_ID`, so lead, child and standalone summarization calls share affinity; distinct runs get distinct namespaces. Interactive background calls lacking LangGraph thread context still fall back to `background`, and require host qualification before cross-conversation affinity is claimed. [run-e2e.sh](run-e2e.sh) invokes the pinned `inspect eval e2e/gaia.py@deerflow_gaia`, serially (`--max-samples 1`), with logs and `INSPECT_EVALS_CACHE_DIR` outside the checkout. The actual worker model is copied from private host configuration into Inspect's run metadata. Inspect itself makes no generation call. [run.py](e2e/run.py) launches a fresh labeled embedded-worker container, retains every native attempt, captures raw events outside its mounts, and bounds the subprocess to 2,100 seconds. Nonzero exits, incomplete outputs and unconfirmed cleanup become Inspect errors, never incorrect answers fabricated by the adapter. `check.py`'s successful transport status and the Inspect CLI's successful process exit are **not a passing GAIA score**; read `gaia_scorer` results in the native `.eval` log. The pre-grader receipt deliberately records `grader.verdict: null` and points to that log.

The scorer gives upstream correctness/accuracy; it does not supply a paired non-inferiority conclusion or establish a token saving. No A/B or superiority result was measured here.
