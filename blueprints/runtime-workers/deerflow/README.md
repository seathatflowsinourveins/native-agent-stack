DeerFlow 2.1.0 is a **draft multi-agent runtime-worker recipe**, powered by GPT-6 through the local OmniRoute gateway. The deliverable is configuration, installation instructions, and a frozen research-and-code acceptance task. Source inspection and offline integration checks are evidence for this recipe; Docker startup, model calls, and runtime acceptance must be measured by the coordinator. No host installation, image pull, service start, production-service modification, or live E2E was performed while building it. This belongs to `lane:foundation`; the trading DeerFlow/codex-acp recipe is reference only.

The rootless Compose deployment publishes **only nginx, at `127.0.0.1:3771`**. Backend, frontend, nginx, and Redis startup scripts choose their container's private interface explicitly. There is no host-network mode and no Docker socket mount. Rootless Docker/Compose are prerequisites supplied separately, not installed by this recipe. Docker verifies content-addressed image layers; the installer also checks returned `RepoDigests` and the release image revision labels, saving private post-pull image metadata. It downloads the source archive only after defining its SHA256, checks both upstream lockfile hashes, and creates its prefix at `$HOME/.local/share/codex-ecosystem/tools/deerflow-2.1.0`. All writable application/MCP/cache/run state lives below `$HOME/.local/state/native-agent-stack/runtime-workers/deerflow`, with private directories mode 0700 and configuration files mode 0600. Shared MCP dependency mounts are read-only; QMD queries use an owned writable snapshot of the adopted index.

For code execution, the chosen provider is **upstream `deerflow.sandbox.local:LocalSandboxProvider` inside the gateway container**, with `sandbox.allow_host_bash: true`. Its paths are scoped per thread, but it is a trusted single-user worker: code and stdio MCP processes share the gateway container and can reach that worker's mounted data. It is not per-thread process isolation. [config.example.yaml:1436–1472](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/config.example.yaml#L1436-L1472) documents the setting and the container-relative mount requirement; [LocalSandboxProvider:36–70](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/backend/packages/harness/deerflow/sandbox/local/local_sandbox_provider.py#L36-L70) states its isolation limits.

Upstream's AIO provider would require controlling Docker from the backend through the opt-in [DooD overlay:1–26](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/docker/docker-compose.dood.yaml#L1-L26). Exposing the rootless socket gives the backend control over that user's Docker daemon, containers, and volumes. It does not by itself give host root access. The reviewed [AIO backend selection:253–284](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/backend/packages/harness/deerflow/community/aio_sandbox/aio_sandbox_provider.py#L253-L284) selects a Kubernetes provisioner or a local Docker manager; a static AIO `sandbox.base_url` connector was not found there. Native backend plus AIO avoids a socket inside a container but runs MCP processes on the host. Kubernetes, E2B, and [OpenSandbox](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/backend/packages/harness/deerflow/community/opensandbox/README.md#L7-L40) add services not established by the supplied host facts. Those are alternatives when stronger per-thread isolation becomes a requirement.

The header extension uses a private LangChain payload hook, so it is pinned to the resolved package and must be requalified on an upgrade. The host preflight inspects two actual payloads without sending them. A live run must still establish streaming, upstream max, header forwarding, and prompt-cache behavior; no savings are claimed from configuration alone. OmniRoute supplies no embeddings: SocratiCode retains the adopted local embedding service, and QMD uses lexical retrieval from its local index without loading or downloading models.

**Private host preparation is necessary before running the installer.** Copy [host.json.example](host.json.example) to a mode-0600 file outside the checkout. Fill the Docker executable, adopted ecosystem root, actual local Qdrant/embedding endpoints, and narrow same-path mounts for the existing MCP binaries, their pinned tool prefixes, and interpreter targets, plus the source QMD database and its four collection definitions. Stdio programs run inside the backend image, so a host registration alone cannot make them available. Do not mount the whole home, ecosystem root, credential stores, Docker socket, or the recipe prefix. Executable symlinks must resolve inside the container; any external Python/Node interpreter target needs its own read-only mount. `qmd_snapshot` supplies an existing named index database and exactly those four collection definitions. The installer uses SQLite backup from a read-only source connection to create a consistent snapshot, including live WAL contents, under owned `/state/mcp/qmd`. It rejects other or empty collections, never indexes or refreshes the shared source, and preserves an existing snapshot on reinstall. The `.yml` configuration is JSON-compatible YAML containing only path/pattern definitions; update hooks and editor settings are omitted. Native QMD requires a writable database/cache even for queries, so the shared original is never used directly. Names and paths follow [QMD v2.8.3 collections.ts:101–125](https://github.com/tobi/qmd/blob/v2.8.3/src/collections.ts#L101-L125) and [store.ts:636–653](https://github.com/tobi/qmd/blob/v2.8.3/src/store.ts#L636-L653). Original source document paths need not be mounted for retained database retrieval. Snapshot refresh is a separate explicit host action. QMD inherits the adopted Node PATH to preserve the native-module ABI. Missing dependencies fail the preflight; the recipe does not invent a download command or mutate the adopted host installs to fix them.

`install.sh` is idempotent for the same pins: it verifies cached source and images, retains existing private secrets/session namespace, refuses to replace unrelated skill directories, and renders worker-owned files. It starts no services. `check` runs a temporary backend container, discovers MCP tools, and calls QMD's read-only status tool; it is a **local integration preflight, not model or research/coding acceptance**. `upstream-tests` selects unchanged `tests/test_model_factory.py`, `tests/test_mcp_client_config.py`, and `tests/test_client.py` with the upstream `uv run pytest -m 'not live'` pattern from [backend/Makefile:20–26](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/backend/Makefile#L20-L26). That subset and its environment must be recorded separately from the local recipe tests; it does not replace upstream's full non-live suite. `up` starts the private Compose project. The interactive UI's native first-run setup remains native. The frozen E2E uses the official embedded client directly, so it does not need browser login or a running UI. Generated model and extension configuration is mounted read-only; changing MCP settings or skill enablement through the interactive UI is outside this recipe and may fail. Edit the owned templates/private host configuration and rerun the installer instead.

`down` stops only this Compose project and retains its state. Re-run `up` to restart. Re-running the installer repairs generated recipe files while retaining the pinned source and private run evidence. Failed E2E attempts remain under owned `runs/`; a private `last-run` file points to the latest attempt. Preserve receipts before manually removing the exact prefix and state directories to uninstall. No pruning, unrelated container deletion, credential deletion, or automatic state wipe is performed. Restart/recovery/persistence are **pending host acceptance**, not established by these commands being present.

[run-e2e.sh](run-e2e.sh) uses [DeerFlowClient.stream](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/backend/packages/harness/deerflow/client.py#L770-L910). The run gate also requires a successful deterministic check, two completed child results confirmed by native `subagent_status` metadata, both actual skill reads, both Context Mode result events, and a Responses/max row in the gateway window. All native child failure statuses, including `polling_timed_out`, remain counted even when their text is empty or error-prefixed: [status contract:67–89](https://github.com/bytedance/deer-flow/blob/345f08be00c8a9495079b732a39b46aa9af1584e/backend/packages/harness/deerflow/subagents/status_contract.py#L67-L89). Tool result events establish that a result returned; they do not by themselves establish its semantic success. Child-only events are not silently inferred from lead traces.

[receipt.py](e2e/receipt.py) reads the live `$HOME/.local/share/omniroute/storage.sqlite` with `mode=ro`, preserving WAL visibility. An SQLite authorizer permits only `call_logs` and **timestamp, path, status, model, reasoning_effort_requested, reasoning_effort_upstream, tokens_in, tokens_cache_read, tokens_reasoning**; no other table or column is queried. [SQLite URI documentation](https://www.sqlite.org/uri.html) explains why `immutable=1` is inappropriate for this live database; [Python's authorizer API](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.set_authorizer) supplies the read guard. Unavailable schema/database and zero rows remain explicit unknown/failure states. Only validated fields, tool/skill names and counts, public version/pins, times, and check results enter receipts. Raw prompts, tool arguments/results, host paths, emails, thread/call IDs, and private configuration stay private. The nine allowed columns cannot correlate a session: **window rows may include other workers' concurrent traffic**, and no gateway usage total is attributed to this worker. Quiescent-window or independent gateway-owner verification is still required for exclusive attribution. Cache-read and reasoning counters remain separate; no token saving or whole-run cost is inferred.
