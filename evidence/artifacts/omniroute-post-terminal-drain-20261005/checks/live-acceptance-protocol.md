# Live acceptance of the drain build on 20128: the protocol, version 2, frozen before the switch (2026-10-06)

This file is frozen by the commit that adds it, before the canary switch. It fixes the inputs, the commands, the repetitions, the expected outcomes, the guards and the rollback triggers (`docs/acceptance-evidence-policy.md`, "Preserve the returned result").
A run that misses an expected outcome is recorded as a failed or inconclusive attempt and is not repeated until it is green; the only repeat the protocol allows is the one named under "Inconclusive, void, fail, rollback".
Version 1 of this protocol and of its scripts (committed at `c62df3a8d`, pushed at `bcb09e8b8`) is superseded; its scripts and its baseline results are kept (`superseded/`, `checks/live-acceptance-baseline-v1-*.txt`). "Amendments" at the end lists what changed and why. After the full-scope read of `8f9d89662` (round 9: 0 P1, 6 P2, 8 P3) the pre-switch guard is version 5 and a row-level census of the canary window (`scripts/window-census.py.txt`) runs after the arms; both are new and NOT frozen, and no byte of raw script 2.2, native script 2.1, the identity read-back or the wrapper changed (the command center's ruling, option (b)): see "Row-level census of the window" and the last amendment.

## What it decides, and what it does not

**Decides:** whether the drain build, running as the 20128 unit, persists the `call_logs` and `usage_history` rows of every request of a client that closes right after the terminal event: for Responses clients (raw clients, and the native `codex exec` in its one-request and its tool-call shapes) and for a
Chat Completions client (a non-Responses format); whether a client that reads to the end or closes later is still logged (no regression); and whether the switch changes the effort the gateway sends upstream. The switch moves 20128 from build `cf6748d04`
(v3.8.51 release branch + #13788 + the affinity patch + PR 15167 head `f5d8e150b`) to the drain build `2a41147b7` (v3.8.51 tag + the affinity patch + PR 15167 head `0585aba55` + the drain patch, no #13788), so the 12 files that only the newer PR head has
(`effortStandardization.ts` and the Responses translator helpers among them) are exercised by the effort probes.

**Does not decide:** Anthropic-format (`message_stop`) clients (the drain applies to them by code reading; no test or probe runs one); a client that closes while the upstream tail outlasts the 10 s grace period (it still leaves neither a 200 nor a 499 row,
by design of this patch; see the record's "What the patch does not close"); the 2604 host (its install has its own read-back); the gateway's pending-request counter (observed and recorded, not gated).

## Row-level census of the window (new in the round after the full-scope read of `8f9d89662`, hardened after that of `6b734c6bf`; a gate on top of the scripts' verdicts, not a frozen script)

The scripts judge each request alone, and `usage_history` has no request key: a usage row is tied to a request only by its metadata (model, token counts, time, provider, account, endpoint, latency, time to first token). One foreign request's row with the same metadata could therefore stand in for an own request's dropped row. The command center's ruling (option (b)) leaves the frozen scripts as they are, records the in-script exclusivity as a residual and closes it for the canary window with this census.
`scripts/window-census.py.txt` runs once after the four arms, read-only on the gateway's store (SQLite `mode=ro`), on the arms' PRIVATE outputs (the committed copies have their ids shortened and are refused) and the guard 5 `--idle-only` receipt of step 7b. It prints every measurement and ends 0 PASS, 2 INCONCLUSIVE (it never says FAIL: the scripts judge the rows) or 3 for a usage error.
Over the window from the idle receipt's end to 5 s after the last arm's end it requires: (i) every call row is an own row, found by the tag the scripts printed (raw: correlation id or response id; native: the `X-OmniRoute-Session-Id`) with the scripts' own predicates; every other `call_logs` row is foreign whatever its path (the gateway's own `/api/providers/test` rows are listed and make the window INCONCLUSIVE), call rows are read over the same 3 s pad before the window's start as the usage rows (a foreign request that finished just before the window has its usage row there); and, exactly and wherever it lies (the pad alone leaves a sliver at its edge), every call row that is not this run's and could own a usage row that an own call row can claim (the scripts' candidate query seen from the usage row: the same model and token counts within 3 s, and the scripts' own association) makes the window INCONCLUSIVE; a request that carries no full id cannot be attributed;

"Idle for the whole window" means two things together: the guard was clean at the window's start, AND no foreign call row and no orphan usage row exists over the whole tiled window. The guard's observation (30 s by default) does not observe a 32-minute window by itself, and it cannot see a request that is silent on the wire (the live trial's mid-arm run, `checks/guard-live-trial.txt`, shows one connection classified idle: the stream of a request whose terminal event had been delivered 20 s earlier and which the gateway keeps open for about a minute longer, silent on the wire).
What it cannot exclude: the rows alone cannot attribute a usage row to its request (`usage_history` has no request key), and the association tolerates numbers that are not identical (a latency within 100 ms; a time to first token within 1 ms, or not compared at all when either side is NULL, which is routine on this host (`checks/census-calibration-measurements.txt`); within 3 s of the own call row). The census therefore reads a second record that does not depend on the rows: the gateway's own journal (`journalctl --user -u omniroute.service -o json --all`, `--since` and `--until` with an explicit UTC suffix: without it journalctl reads local time; without `--all` it writes a field over 4096 bytes as null), in which the gateway logs one line (`tag=HTTP method=POST`, message `📥 POST ...`) when a request ARRIVES, whatever happens to its call and usage rows afterwards. It counts those lines by the gateway's own clock (the line's `time`, which must lie between 1 s after and 30 s before journald's receive stamp: review 4, P3-6) from 4 s before the window's start to 4 s after its end (the usage pad plus 1 s; the store side reads rows 3 s beyond the window on both sides; the width is not a bound on a request's arrival, which can precede its estimated start by a delay that nothing bounds: r12-P2-1), requires exactly as many as there are own call rows and pairs each own call row with a distinct line of the same path that arrived within 3 s of its timestamp minus its duration (what was measured on this host's rows, and why the parameters were chosen, is in `checks/census-calibration-measurements.txt`, produced by `scripts/census-calibration.py.txt`; those figures are not enforced invariants). A foreign request, a request whose call row was never written and an own request that lost its rows each leave a line without a matching row. On the baseline arms this gives the same answer as the scripts: 43 inbound requests (the scripts made 17, 6, 4 and 16), 26 own call rows, and the 17 lines without a row are the 17 dropped requests. What stays outside is the untested boundary, which the census receipt states verbatim (its `UNTESTED-BOUNDARY` line, refined by `UNTESTED-BOUNDARY-DETAIL`) next to its evidence classes (its `EVIDENCE-CLASS` line: local_integration and synthetic controls, plus the stated real rows; controls J21a and J21b): (1) a foreign request that the gateway did not log or journald did not keep (a rate limit, a vacuum), while every own request's line is present; (2) a lost own line balanced by a same-path foreign line within 3 s, per link of a chain (for the arrival lines the 3 s is measured from the lost request's ESTIMATED start, not from its physical arrival, which may be earlier by a delay that nothing bounds, so two lines of the same two requests may lie further apart: a displacement of 5.5 s was reproduced, control J27a; for the stream-end lines the tolerance is 0.25 s on the implied start and the pairing needs the same provider and model; the chain width is 3 s per link, controls J10 and J15); (3) an unlogged persistence failure (a save skipped while disk persistence is off or while saves are closing, the usage insert's same-millisecond dedup); and traffic that is not an inbound POST. A request is covered by the stream-end record only when it passes the HTTP stream controller of chatCore: a non-streaming foreign request prints no stream-end line and its arrival line does not bound it (the delay before its duration clock starts is unbounded: the gateway logs the arrival before the policy work, the credential refresh and, for a combo, the failed attempts), so it is covered by neither record and can only stand in for an own row when its clock also started within 0.25 s of the own call row's (control J22e). A Responses-over-WebSocket turn (the canary tarball ships `dist/server-ws.mjs`; the gateway's WebSocket proxy writes its rows through `POST /api/internal/codex-responses-ws`, both stamped at the turn's START, with the turn's length as duration and latency) writes neither line either, so it is covered by neither record: a call row of one (method `WEBSOCKET` or request_type `responses_websocket`) whose start and duration reach the window padded by the usage pad makes the window INCONCLUSIVE (review 4, F1; J30a-J30l), and a turn whose call row was lost as well is a case of items (1) and (3) above (an OWN native turn that a future Codex client sent over WebSocket would be refused the same way, and its missing arrival line would fail the journal pairing anyway: the native script's `codex exec` turns are HTTP today, and the retained baselines and the live store hold 0 WebSocket rows). The serving process, its start and the holders of the store are read at one point in time (a transient listener or writer inside the window is not seen); journald's drops are bounded only by the unit's entry rate against its limit, and a vacuum or rotation gap is not detected. The wrapper's journal line per arm (`Failed to save call log`) covers only the call-log save's logged failure (the usage path logs a different line, `Failed to save usage stats`). A PASS means: every own request's rows are present and paired one to one; no row of any other request was seen in the window (the exact check covers its edges); the journal's inbound-request lines and its stream-end controllers pair one to one with the own requests (what stays outside is stated above); the guard was idle at the window's start; the serving process was the same (its listener, its start, the writer of the request lines); and the wrapper's journal line was 0. It is not a proof against a gateway that logs nothing: then the own requests' lines are missing too, and the window is INCONCLUSIVE. The numbers the association cannot compare are refused rather than passed (a non-finite or negative latency or time to first token, a time to first token longer than the latency: Y13a, Y13b), and the scripts' `associated()` is kept byte for byte.
What is known about how likely it is: on the unpatched build a request that lost its rows lost BOTH (`checks/live-acceptance-baseline-race.txt`), and in the 32-minute baseline window the census found 26 call rows and 26 usage rows, every usage row associated with an own call row, no foreign row and no orphan (`checks/census-baseline-real-data.txt`), so a usage row without its call row has no observed case here: it would need a call-row write that failed or was skipped while the usage write succeeded, and the journal's inbound-request lines would show the request either way (43 lines for the baseline's 43 requests).
The census was also run on a live quiet window (`checks/census-live-trial.txt`): on arm A alone the store-side measurements are an exact match (2 own call rows, 2 usage rows, 0 foreign, 0 orphans) and the journal check refuses it (3 inbound requests against 2 own call rows: arm B's first request arrived 0.44 s after arm A's end, inside the 5 s settle, and left no row on the unpatched build, so the store cannot see it and the journal does); on the three arms it is INCONCLUSIVE (6 inbound requests, 3 own call rows). No live PASS exists yet: the exact-match PASS is shown by the controls (P1, P4) and needs a window in which nothing follows the last arm. It does not make the in-script association exclusive and it judges no request.

## Inconclusive, void, fail, rollback

- INCONCLUSIVE (a raw sample that does not exercise its mode, a native turn that did not complete or lacks what the shape needs, an ambiguous usage match, a script error, no SUMMARY line, a census exit status of 2): the INCONCLUSIVE requests or turns are repeated once, as a smaller invocation with the same argument vector and the missing count, in a quieter window; for a census INCONCLUSIVE the repeat is the whole acceptance (a new idle receipt, the four arms, a new census), because the census judges the window, not a request;
  a repeat that is again INCONCLUSIVE counts as NOT ACCEPTED. The scripts print their value-free diagnostics for every such turn (event types, stdout and stderr tails, the rows stored under the session id); they stay in the folder with the run.
- VOID (the gateway's identity changed during a run, was unreadable, or was not the build under test): a restart of the unit, a change of prefix or a failed health read during the acceptance means the build under test was not stable: roll back.
- Roll back at once (`python3 switch_gateways.py --rollback <the switch directory it printed>`, which restarts only 20128 to the baseline prefix) on any of: a FAIL (an effort group FAILs when an observed effort column differs from the baseline's observed value; an unobserved attempt is not a difference); a VOID; a health failure of the unit; a `Failed to save call log` line; NOT ACCEPTED; no complete acceptance within 2 hours of the switch.
  The failed run is kept as recorded.
- After ANY rollback: `gateway-identity.py --expect-prefix omniroute-3.8.51-2f42a9ac-pr13788-affinity2-pr15167 --expect-build cf6748d04` must exit 0 (health ok), `show-log-receipt.py` is run again, and 20129 must still run `omniroute-3.8.51-2f42a9ac-pr13788` (`87c4c488d`). 20129 is not switched at any point.
- After a pass, the unit's journal is scanned over 30 minutes of normal lane traffic (the journal command above): zero `Failed to save call log` lines, and the receipt after the switch shows the same drop-in declaration, a new `MainPID`, health ok and no credential-shaped strings except the known `[ModelSync]` account labels.

## Queueing

The PR is queued only after every gated request and turn of the canary passed at both reads (the wrapper's exit status 0), the census passed (exit 0, `scope=canary`), the 30-minute journal scan is clean and the after-switch receipt is recorded, all in `checks/`. On a FAIL, a VOID or a rollback the record is amended first (the candidate was rolled back, why, with the failed run kept as recorded) and the PR is not queued on the strength of "the results are in".
A canary that passed only as a no-regression check (the pre-switch control found the race set unable to discriminate) is recorded as that and does not support adoption.

## Records kept

For every run: the exact argument vector, the working directory, the start and end times, the script sha256 (all on the `FROZEN` line), the exit code (the `SUMMARY` line, `exit=` and `RUN-STATUS`), the identity before and after, the journal count, the pending-counter delta and the full stdout, as `checks/live-acceptance-canary-*.txt` next to the baselines
(the committed copy shortens UUID-shaped correlation ids to their first 8 hex digits, because the repository's publication check rejects full UUIDs, and starts with a note carrying the sha256 of the unshortened text; the unshortened outputs of the baselines, the controls and the canary are kept gzipped in the first host's private artifact directory and listed with their sha256 in `checks/logs/MANIFEST.txt`). The idle receipt and the census receipt are kept as `checks/live-acceptance-canary-guard-idle.txt` and `checks/live-acceptance-canary-census.txt` (the census prints ids as 8 hex characters only).
The unit's state before and after the switch is kept value-free (`systemctl --user show` fields, the receipts, the identity lines). Failed, inconclusive and void runs stay in the folder.
