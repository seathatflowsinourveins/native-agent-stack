# Live acceptance of the drain build on 20128: the protocol, version 2, frozen before the switch (2026-10-06)

This file is frozen by the commit that adds it, before the canary switch. It fixes the inputs, the commands, the repetitions, the expected outcomes, the guards and the rollback triggers (`docs/acceptance-evidence-policy.md`, "Preserve the returned result").
A run that misses an expected outcome is recorded as a failed or inconclusive attempt and is not repeated until it is green; the only repeat the protocol allows is the one named under "Inconclusive, void, fail, rollback".
Version 1 of this protocol and of its scripts (committed at `c62df3a8d`, pushed at `bcb09e8b8`) is superseded; its scripts and its baseline results are kept (`superseded/`, `checks/live-acceptance-baseline-v1-*.txt`). "Amendments" at the end lists what changed and why. After the full-scope read of `8f9d89662` (round 9: 0 P1, 6 P2, 8 P3) the pre-switch guard is version 5 and a row-level census of the canary window (`scripts/window-census.py.txt`) runs after the arms; both are new and NOT frozen, and no byte of raw script 2.2, native script 2.1, the identity read-back or the wrapper changed (the command center's ruling, option (b)): see "Row-level census of the window" and the last amendment.

## What it decides, and what it does not

**Decides:** whether the drain build, running as the 20128 unit, persists the `call_logs` and `usage_history` rows of every request of a client that closes right after the terminal event: for Responses clients (raw clients, and the native `codex exec` in its one-request and its tool-call shapes) and for a
Chat Completions client (a non-Responses format); whether a client that reads to the end or closes later is still logged (no regression); and whether the switch changes the effort the gateway sends upstream. The switch moves 20128 from build `cf6748d04`
(v3.8.51 release branch + #13788 + the affinity patch + PR 15167 head `f5d8e150b`) to the drain build `2a41147b7` (v3.8.51 tag + the affinity patch + PR 15167 head `0585aba55` + the drain patch, no #13788), so the 12 files that only the newer PR head has
(`effortStandardization.ts` and the Responses translator helpers among them) are exercised by the effort probes.

**Does not decide:** Anthropic-format (`message_stop`) clients (the drain applies to them by code reading; no test or probe runs one); a client that closes while the upstream tail outlasts the 10 s grace period (it still leaves neither a 200 nor a 499 row,
by design of this patch; see the record's "What the patch does not close"); the 2604 host (its install has its own read-back); the gateway's pending-request counter (observed and recorded, not gated).

## Row-level census of the window (new in the round after the full-scope read of `8f9d89662`, hardened after that of `6b734c6bf`; a gate on top of the scripts' verdicts, not a frozen script)

The scripts judge each request alone, and `usage_history` has no request key: a usage row is tied to a request only by its metadata (model, token counts, time, provider, account, endpoint, latency, time to first token). One foreign request's row with the same metadata could therefore stand in for an own request's dropped row. The command center's ruling (option (b)) leaves the frozen scripts as they are, records the in-script exclusivity as a residual and closes it for the canary window with this census.
`scripts/window-census.py.txt` runs once after the four arms, read-only on the gateway's store (SQLite `mode=ro`), on the arms' PRIVATE outputs (the committed copies have their ids shortened and are refused) and the guard 5 `--idle-only` receipt of step 7b. A journal query that fails (a non-zero exit) is not a clean zero: the line says `JOURNAL-UNAVAILABLE` and the run is INCONCLUSIVE (control W10); a start timestamp that cannot be read as a date stops the wrapper with exit 4 before it runs anything (W11). The scan by hand, at the end of the acceptance and again 30 minutes later, is `bash journal-save-failures.sh` (`scripts/journal-save-failures.sh.txt`, run from a copy without the suffix; new after the read of `ec4b489d9`, finding 3: the pipeline `journalctl ... | grep -c 'Failed to save call log'` typed by hand prints the same `0` with the same status when journalctl fails with empty output as when it reads a clean journal, control D0 of `checks/journal-save-failures-controls.txt`; the same on the host's real journalctl: R1 and R2 of `checks/journal-save-failures-live-read.txt`). It writes the unit's journal since the unit's ExecMainStartTimestamp to a file, checks journalctl's exit status and its stderr, and only then counts: exit 0 is a clean scan (`journal_failed_to_save_call_log=0`); exit 1 a count above zero (a rollback trigger on the canary); exit 2 `JOURNAL-UNAVAILABLE` (journalctl exited non-zero, or exited 0 with a stderr line that holds a word of the census's `JOURNAL_STDERR_ALARM`, or exited 0 and printed nothing (a unit that does not exist or a start in the future reads the same, and the pipeline above would print `0`), or the start timestamp could not be read or is not a date): INCONCLUSIVE, so no acceptance and no queueing on it, and the scan is repeated once the journal can be read; exit 3 a usage error (controls C1-C13b of the same file). The wrapper's check does not read journalctl's stderr: a journal file that journalctl skips with exit 0 is caught by the census's journal check and by the scan, not by the wrapper.
Each wrapper run's status: 4 VOID, 1 FAIL (a script exit 1, or a journal count above zero), 2 INCONCLUSIVE (a script exit 2 or 3, no SUMMARY line, or an unreadable journal), else 0; the wrapper exits with the first that applies of 4, 1, 2, 0.

## Inconclusive, void, fail, rollback

- INCONCLUSIVE (a raw sample that does not exercise its mode, a native turn that did not complete or lacks what the shape needs, an ambiguous usage match, a script error, no SUMMARY line, a census exit status of 2): nothing is accepted from a partial result. A fresh COMPLETE four-arm acceptance replaces an INCONCLUSIVE arm: a new idle receipt, the four arms with their whole inventory (17 raw requests, 6 race requests, 4 one-request native turns and 8 tool-call native turns: the `RESULT` records, one `SUMMARY` and one `RUN-STATUS` of a successful run per arm, the wrapper exiting 0) and a new census over the tiled window, because the census judges the window and its inventory, not a request: a smaller invocation with the missing count (a last arm of one turn: the inventory (17, 6, 4, 1)) is INCONCLUSIVE with exit 2, and a failed `SUMMARY` or `RUN-STATUS` cannot be repaired by adding another run's output to the arm's file (a hand-concatenated output is refused). A smaller invocation with the same argument vector and the missing count is DIAGNOSTIC only (it may show what failed, in a quieter window) and is never part of an acceptance. A new gateway incarnation (a restart of the unit, then the idle receipt of that incarnation) is needed before the fresh acceptance when the INCONCLUSIVE named a defect of the incarnation, which a new window in the same incarnation cannot clear: an inbound request line since the serving process's start with no call row of its path (a retained rowless arrival keeps invalidating the incarnation until the process restarts: the unpatched build's rowless lines are such, and so is a request that the gateway rejected before its call log), a second database open, a step of the wall clock since the listener's birth (restart the gateway after the host's last sleep), several attempt rows of one request, a missing or shared correlation id; an INCONCLUSIVE of the window alone (a foreign call row in it, an idle receipt that is not clean, an arm that did not complete) needs a new idle receipt and a new window in the same incarnation;
  a fresh acceptance that is again INCONCLUSIVE counts as NOT ACCEPTED. The scripts print their value-free diagnostics for every such turn (event types, stdout and stderr tails, the rows stored under the session id); they stay in the folder with the run.
- VOID (the gateway's identity changed during a run, was unreadable, or was not the build under test): a restart of the unit, a change of prefix or a failed health read during the acceptance means the build under test was not stable: roll back.
- Roll back at once (`python3 switch_gateways.py --rollback <the switch directory it printed>`, which restarts only 20128 to the baseline prefix) on any of: a FAIL (an effort group FAILs when an observed effort column differs from the baseline's observed value; an unobserved attempt is not a difference); a VOID; a health failure of the unit; a `Failed to save call log` line; NOT ACCEPTED; no complete acceptance within 2 hours of the switch.
  The failed run is kept as recorded.
- After ANY rollback: `gateway-identity.py --expect-prefix omniroute-3.8.51-2f42a9ac-pr13788-affinity2-pr15167 --expect-build cf6748d04` must exit 0 (health ok), `show-log-receipt.py` is run again, and 20129 must still run `omniroute-3.8.51-2f42a9ac-pr13788` (`87c4c488d`). 20129 is not switched at any point.
- After a pass, the unit's journal is scanned over 30 minutes of normal lane traffic (`bash journal-save-failures.sh`, above): it must exit 0 with `journal_failed_to_save_call_log=0` (exit 1, a count above zero, is a rollback trigger; exit 2, `JOURNAL-UNAVAILABLE`, is no observation: INCONCLUSIVE, no acceptance and no queueing on it), and the receipt after the switch shows the same drop-in declaration, a new `MainPID`, health ok and no credential-shaped strings except the known `[ModelSync]` account labels.

## Queueing

The PR is queued only after every gated request and turn of the canary passed at both reads (the wrapper's exit status 0), the census passed (exit 0 and `scope=canary` exactly, never `scope=canary-fixture`), the 30-minute journal scan is clean (`bash journal-save-failures.sh` exited 0 and printed `journal_failed_to_save_call_log=0`; a `JOURNAL-UNAVAILABLE` line, exit 2, is not a clean scan) and the after-switch receipt is recorded, all in `checks/`. On a FAIL, a VOID or a rollback the record is amended first (the candidate was rolled back, why, with the failed run kept as recorded) and the PR is not queued on the strength of "the results are in".
A canary that passed only as a no-regression check (the pre-switch control found the race set unable to discriminate) is recorded as that and does not support adoption.
