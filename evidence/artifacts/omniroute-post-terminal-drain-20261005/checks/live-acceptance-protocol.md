# Live acceptance of the drain build on 20128: the protocol, version 2, frozen before the switch (2026-10-06)

This file is frozen by the commit that adds it, before the canary switch. It fixes the inputs, the commands, the repetitions, the expected outcomes, the guards and the rollback triggers (`docs/acceptance-evidence-policy.md`, "Preserve the returned result").
A run that misses an expected outcome is recorded as a failed or inconclusive attempt and is not repeated until it is green; the only repeat the protocol allows is the one named under "Inconclusive, void, fail, rollback".
Version 1 of this protocol and of its scripts (committed at `c62df3a8d`, pushed at `bcb09e8b8`) is superseded; its scripts and its baseline results are kept (`superseded/`, `checks/live-acceptance-baseline-v1-*.txt`). "Amendments" at the end lists what changed and why. After the full-scope read of `8f9d89662` (round 9: 0 P1, 6 P2, 8 P3) the pre-switch guard is version 5 and a row-level census of the canary window (`scripts/window-census.py.txt`) runs after the arms; both are new and NOT frozen, and no byte of raw script 2.2, native script 2.1, the identity read-back or the wrapper changed (the command center's ruling, option (b)): see "Row-level census of the window" and the last amendment.

## What it decides, and what it does not

**Decides:** whether the drain build, running as the 20128 unit, persists the `call_logs` and `usage_history` rows of every request of a client that closes right after the terminal event: for Responses clients (raw clients, and the native `codex exec` in its one-request and its tool-call shapes) and for a
Chat Completions client (a non-Responses format); whether a client that reads to the end or closes later is still logged (no regression); and whether the switch changes the effort the gateway sends upstream. The switch moves 20128 from build `cf6748d04`
(v3.8.51 release branch + #13788 + the affinity patch + PR 15167 head `f5d8e150b`) to the drain build `2a41147b7` (v3.8.51 tag + the affinity patch + PR 15167 head `0585aba55` + the drain patch, no #13788), so the 12 files that only the newer PR head has
(`effortStandardization.ts` and the Responses translator helpers among them) are exercised by the effort probes.

**Does not decide:** Anthropic-format (`message_stop`) clients (the drain applies to them by code reading; no test or probe runs one); a client that closes while the upstream tail outlasts the 10 s grace period (it still leaves neither a 200 nor a 499 row,
by design of this patch; see the record's "What the patch does not close"); the 2604 host (its install has its own read-back); the gateway's pending-request counter (observed and recorded, not gated).

That rule judges ONE request at a time: it cannot tell that a foreign row it accepted for one request might equally be the row of another, or that a foreign row stands in for a dropped own row (full-scope read of `8f9d89662`, P2-1). ## Row-level census of the window (new in the round after the full-scope read of `8f9d89662`; a gate on top of the scripts' verdicts, not a frozen script)

The scripts judge each request alone, and `usage_history` has no request key: a usage row is tied to a request only by its metadata (model, token counts, time, provider, account, endpoint, latency, time to first token). One foreign request's row with the same metadata could therefore stand in for an own request's dropped row. The command center's ruling (option (b)) leaves the frozen scripts as they are, records the in-script exclusivity as a residual and closes it for the canary window with this census.
`scripts/window-census.py.txt` runs once after the four arms, read-only on the gateway's store (SQLite `mode=ro`), on the arms' PRIVATE outputs (the committed copies have their ids shortened and are refused) and the guard 5 `--idle-only` receipt of step 7b. It prints every measurement and ends 0 PASS, 2 INCONCLUSIVE (it never says FAIL: the scripts judge the rows) or 3 for a usage error.
Over the window from the idle receipt's end to 5 s after the last arm's end it requires: (i) every call row is an own row, found by the tag the scripts printed (raw: correlation id or response id; native: the `X-OmniRoute-Session-Id`) with the scripts' own predicates; every other `call_logs` row is foreign whatever its path (the gateway's own `/api/providers/test` rows are listed and make the window INCONCLUSIVE), call rows are read over the same 3 s pad before the window's start as the usage rows (a foreign request that finished just before the window has its usage row there), and a request that carries no full id cannot be attributed;
(ii) exactly one own call row per raw request, at least the printed `min_rows` per native turn, and own call rows and usage rows that form connected components with as many usage rows as call rows and exactly ONE perfect matching each (the candidate query and the association rule of the scripts, copied byte for byte and checked against them in the controls); (iii) no orphan usage row: every usage row of the window, read from 3 s before to 3 s after it, is associated with an own call row, and no group of usage rows has identical metadata (a duplicated row, or requests the association cannot tell apart);
(iv) the idle receipt is guard version 5, `--idle-only` in its standard invocation (port 20128, unit `omniroute.service`, the default tolerated unit), an observation of at least 30 s, clean, ended before the first arm's own start and not more than 600 s earlier; (v) the clocks agree: every own row lies inside its arm's interval with 2 s of margin (the interval comes from the wrapper's stamps and the scripts' own start and end lines), and the arms do not overlap; (vi) the gateway is the same process throughout: the MainPID and start time in the idle receipt's identity line equal those of every wrapper arm's first identity line (a direct run carries none and is not compared); (vii) the inputs are the frozen scripts' outputs (version and sha256 on the `FROZEN` line, the same store path, a `SUMMARY` line, no VOID, a wrapper header that says `canary`, and with the default four arms the shape raw, raw, native, native), every timestamp of the two tables has the gateway's format (a row of another type or format would be skipped silently by the string bounds), the arm file holds one run (a hand-concatenated output, a RESULT line the census cannot parse and a VOID anywhere are refused) and every arm's `journal_failed_to_save_call_log` is 0 (the wrapper prints that line; a frozen script run directly prints none, and the live trial's runner adds it).
"Idle for the whole window" means two things together: the guard was clean at the window's start, AND no foreign call row and no orphan usage row exists over the whole tiled window. The guard's observation (30 s by default) does not observe a 32-minute window by itself, and it cannot see a request that is silent on the wire (the live trial's mid-arm run, `checks/guard-live-trial.txt`, shows one connection classified idle: the stream of a request whose terminal event had been delivered 20 s earlier and which the gateway keeps open for about a minute longer, silent on the wire).
What it cannot exclude: a usage row of a foreign request whose own call row was never written, with metadata the association cannot tell from an own request's (the same model, token counts, provider, account and endpoint, a latency within 100 ms and a time to first token within 1 ms, within 3 s), standing in for a dropped own usage row (four coincident faults: foreign traffic in a window made quiet on purpose, its call row not written, an own usage row dropped, such a look-alike); the same blindness covers an own call row that was never written while another row stands in for it (its named check is the same journal scan). Its named check is the `Failed to save call log` journal scan that every arm records and the census requires to be 0; the control R3 shows the census passing exactly that case.
What is known about how likely it is: on the unpatched build a request that lost its rows lost BOTH (`checks/live-acceptance-baseline-race.txt`), and in the 32-minute baseline window the census found 26 call rows and 26 usage rows, every usage row associated with an own call row, no foreign row and no orphan (`checks/census-baseline-real-data.txt`), so a usage row without its call row has no observed case here: it would need a call-row write that failed (the journal line) or was skipped while the usage write succeeded.
The census was also run on a live quiet window (`checks/census-live-trial.txt`): PASS on an exact-match arm (2 own call rows, 2 usage rows, 0 foreign, 0 orphans), INCONCLUSIVE on the arms of the unpatched build that lost rows. It does not make the in-script association exclusive and it judges no request.

## Order of steps

1. **Freeze.** This file, the scripts and the baselines are committed and pushed; the coordinator confirms that `git ls-remote origin refs/heads/claude/99-omniroute-drain-patch-20261005` equals that commit. The commit id is the frozen head.
2. **Announce.** Send the frozen head and the planned restart time to 5f, c5 and the command center, and wait for the command center's lift of the hold (a ledger row). 5f confirms that no run of its own is in flight on 20128 at the announced time (its workers and reviews call 20128 too, and the guard fails on a worker of another lane) and holds new GPT launches through 20128 until the acceptance is recorded; c5, the command center's lanes
   and the hindsight services are asked to pause during the acceptance windows (attribution does not depend on it, but a quiet gateway avoids INCONCLUSIVE results from the usage match).
3. **Pre-switch control**, within 15 minutes before the switch: `run-acceptance.sh precontrol <dir>` (the race set and four native two-request turns on the unpatched build, `--expect observe`, bracketed by the identity read-back, which must be the unpatched build). Only valid samples count (HTTP 200, the terminal event received, the early close done, an id to attribute rows by; an HTTP 503 is not a loss). Rule: if it loses fewer than 2 of the 6 valid race requests it cannot discriminate at this hour (fewer than 6 valid samples with fewer than 2 losses is INCONCLUSIVE, exit 2: control W12);
   repeat it once (6 more); if the pooled result is still fewer than 2 of 12, the race set and the early modes are no-regression checks only for this canary, and the fix cannot be demonstrated now: the canary may proceed as a no-regression check, but its record says so and the PR is not queued on it (see "Queueing").
4. **Receipt before:** `show-log-receipt.py` (version 2, an allowlisted output).
5. **Dry run**, required: `python3 switch_gateways.py --only 20128 --prefix-20128 omniroute-3.8.51-c1e30b76-affinity-pr15167-drain-b7c68690 --desc-20128 "<the unit description of the record>" --dry-run` must print all of:
   `20129 omniroute-fw.service: NOT in scope`; `running omniroute-3.8.51-2f42a9ac-pr13788-affinity2-pr15167 (cf6748d04) -> omniroute-3.8.51-c1e30b76-affinity-pr15167-drain-b7c68690 (2a41147b7, shim v2)`; `prefix problems: []`; `dry run: no unit file written, nothing restarted`. Anything else stops the procedure.
6. **Guard and switch, one command line:** `python3 pre-switch-guard.py --switch-tool <the copy of the switch tool> && python3 switch_gateways.py --only 20128 <the same arguments as the dry run> --apply`. The guard exits 0 only when: the switch tool's sha256 is the pinned one; the rollback prefix has `bin/omniroute`, `dist/BUILD_SHA` `cf6748d04` and `shim/lsof` with sha256 `b6ae9002...` and is what the unit runs now (identity read-back, health ok);
   the target prefix has `bin/omniroute`, `dist/BUILD_SHA` `2a41147b7`, the same shim and the drain marker; and for 30 s (6 samples) no worker process of another lane (`omniroute-codex-sdk/worker.py`, `codex exec`, an interactive `codex` naming the omniroute profile or the port), no `call_logs` row in the last 120 s and no ACTIVE client connection to port 20128
   (a connection that carries traffic or queued data during the window, or that is new during it). Every established connection is classified by the owner of its CLIENT end: the 20129 framework gateway (`omniroute-fw.service`, whose cgroup the owner pid is in) holds a connection to 20128 that it replaces about every 25 s (the first watch of `checks/connection-watch-20128.txt`, 05:14-05:16Z: connections of 22-30 s opened by a process of that unit, no call_logs row, no stuck request; the second watch, 06:13Z, saw none, so the poll is intermittent) and is TOLERATED only while the connection is EMPTY (empty queues and no byte received or sent at any sample: the observed poll carries no byte; `--tolerate-unit`), reported and never failed; the same unit also forwards real inference to 20128 through a provider node, so a connection of that unit that carries bytes or queued data is judged like any other client's (ACTIVE, control G13); every other connection must be idle (empty queues, unchanged counters, not new). An `ss` or `pgrep` that fails, or prints what cannot be parsed, fails the check instead of reading as an idle host (controls G14, G15; `pgrep` exiting 1 for no match is not a failure, G16). Guard version 5 (full-scope read of `8f9d89662`, P2-2 and P2-3) parses `ss -O -tnpi` strictly and keys connections by the full normalized tuple of both ends: a record that is malformed or has no TCP-info line, a record seen at one end only, two records that disagree about a tuple and a duplicate tuple fail the check, a malformed or repeated counter and a record with no TCP info (no `mss:` or `cwnd:`) fail the check, while an absent `bytes_sent` or `bytes_received` is zero because `ss` prints them only when they are not zero, and the gateway's end of a connection is the end whose queues and counters are judged (version 4 keyed by client port alone, so two connections that shared a client port overwrote each other and an active connection could read as an empty tolerated one; it read a missing TCP-info line and malformed counters as zeros and dropped a client-only record silently; controls K1-K11 and E1-E6 in `checks/guard5-controls.txt` run version 4's parser next to version 5's on records captured on this host, and G1-G16 were rerun on version 5: `checks/guard5-existing-controls.txt`). The command center asked for "no established client connection"; that cannot hold literally on this host (the framework gateway polls, and before the restart nine idle keep-alive connections from clients in other PID namespaces existed at rest), so the guard tolerates the known poller and idle connections, reports them and fails on active ones: any other service that calls 20128 (hindsight among them) must be PAUSED before the switch (step 2), because its requests show up as active. The guard's live trial is `checks/guard-live-trial.txt`; version 2 of the guard counted the poll as active (its live trial at 05:13Z failed with one ACTIVE connection, and a later trial in a quiet window at 06:13Z was clean: both are in `superseded/guard-live-trial-v2.txt`; control G12 reproduces the failure on the same fixture). It cannot see a request that is silent on the wire (waiting for the upstream) or an interactive client between requests: steps 2 and 3 are not replaceable by it. Keep the rollback directory the switch prints.
7. **After the switch:** the apply output must show `20128: health=True (ok) running prefix=omniroute-3.8.51-c1e30b76-affinity-pr15167-drain-b7c68690 identity_ok=True`, `20129 omniroute-fw.service: untouched; running omniroute-3.8.51-2f42a9ac-pr13788 (87c4c488d)` and `switched: ['20128']`; then `show-log-receipt.py` again (a new MainPID, the same drop-in declaration, health ok).
7b. **Idle receipt**, after step 7 (and after the pre-switch control of step 3, whose requests would be foreign rows), not more than 600 s before the first canary arm and at least 150 s after any hourly provider-test burst: `python3 pre-switch-guard.py --idle-only > <dir>/guard-idle.txt` must exit 0 and end with `IDLE-RESULT clean=True failed_checks=[]`. It is the census's receipt of the window's idle start (the guard's observation without the switch-specific checks; version 5 only).
   Timing: the gateway writes about seven `/api/providers/test` rows in two seconds about 40 s after each start and then once an hour at that minute (observed on 2026-10-06: a unit started at 13:51:19Z wrote bursts at 13:51:55Z, 14:51:56Z, 15:51:58Z, 16:52:00Z and 17:52:02Z; the unit started at 04:26:11Z had written one at 04:26:55Z, and its hourly bursts drifted by about 2 s per hour), and the census counts every call row without an own tag as foreign: the receipt and the four arms (about 32 minutes; the baseline run took 32) must lie between two bursts, so the receipt starts at least 150 s after a burst and the arms end before the next one (about 25 minutes after a burst is the latest start). After a switch the first burst comes about 40 s after the restart, so the receipt can start about 3 minutes after the switch and the acceptance then ends about 36 minutes after the switch, well before the second burst at about 61 minutes.
8. **Acceptance**, within 2 hours of the switch: `run-acceptance.sh canary <dir> <absolute path of the raw baseline file>` (about 32 minutes). Its exit status must be 0.
8b. **Census**, once, after the wrapper, on the four PRIVATE outputs: `python3 window-census.py --guard-receipt <dir>/guard-idle.txt <dir>/live-acceptance-canary-raw.txt <dir>/live-acceptance-canary-race.txt <dir>/live-acceptance-canary-native.txt <dir>/live-acceptance-canary-native-tworequest.txt` must exit 0 (it requires exactly four arm outputs by default, `--require-arms 4`: an omitted arm would leave its requests unattributed). Its receipt is kept as `checks/live-acceptance-canary-census.txt` and the idle receipt as `checks/live-acceptance-canary-guard-idle.txt`; an exit status of 2 is INCONCLUSIVE ("Inconclusive, void, fail, rollback").
9. **After a pass:** the journal command below at the end of the acceptance and again 30 minutes later; the PR is updated with the results (`checks/live-acceptance-canary-*.txt`, the receipts) and queued only under "Queueing".

## Commands (exact argument vectors) and repetitions (frozen)

`run-acceptance.sh` runs these four commands in this order (`<E>` is `observe` for `baseline` and `precontrol`, `all-logged` for `canary`; the canary adds `--baseline <absolute path>` to the first), each bracketed by the identity read-back and followed by the journal check. `P` is the directory of the scripts; the wrapper runs from `/tmp`:

```
# 1 raw set: seventeen requests (responses:early:0 twice, chat:early:0 twice, the other three request kinds once, each effort probe three times)
python3 $P/live-acceptance.py --expect <E> [--baseline <absolute path>] --wait1 12 --wait2 60 \
  responses:eof responses:early:0 responses:early:0 responses:early:0.5 responses:early:2 chat:eof chat:early:0 chat:early:0 \
  effort:cx/gpt-6-astra:max effort:cx/gpt-6-astra:max effort:cx/gpt-6-astra:max \
  effort:cx/gpt-6.1-sol-max effort:cx/gpt-6.1-sol-max effort:cx/gpt-6.1-sol-max \
  effort:cx/gpt-6.1-sol:max effort:cx/gpt-6.1-sol:max effort:cx/gpt-6.1-sol:max
# 2 race set: responses:early:0 six times
python3 $P/live-acceptance.py --expect <E> --wait1 12 --wait2 60 responses:early:0 (x6)
# 3 native, one-request shape: four turns
python3 $P/native-exec-acceptance.py --expect <E> --wait1 12 --wait2 60 --quiet-timeout 120 --exec-timeout 300 astra-max (x4)
# 4 native, tool-call shape: eight turns
python3 $P/native-exec-acceptance.py --expect <E> --wait1 12 --wait2 60 --quiet-timeout 120 --exec-timeout 300 two-request (x8)
```

The `precontrol` kind runs only commands 2 and 4 (with four turns) and prints `PRECONTROL race_lost=<n>/6 race_valid=<v>/6 tworequest_incomplete=<m>/4 tworequest_valid=<w>/4 race_discriminating=<True|False|INCONCLUSIVE>` (INCONCLUSIVE, exit status 2, when there are fewer than 6 valid race samples and fewer than 2 losses).
The journal check, run by the wrapper after every run and by hand at the end of the acceptance and 30 minutes later: `journalctl --user -u omniroute.service --since "<the unit's ExecMainStartTimestamp>" -o cat --no-pager | grep -c 'Failed to save call log'`; any count above zero on the canary is a rollback trigger. A journal query that fails (a non-zero exit) is not a clean zero: the line says `JOURNAL-UNAVAILABLE` and the run is INCONCLUSIVE (control W10); a start timestamp that cannot be read as a date stops the wrapper with exit 4 before it runs anything (W11).
Each wrapper run's status: 4 VOID, 1 FAIL (a script exit 1, or a journal count above zero), 2 INCONCLUSIVE (a script exit 2 or 3, no SUMMARY line, or an unreadable journal), else 0; the wrapper exits with the first that applies of 4, 1, 2, 0.

## Inconclusive, void, fail, rollback

- INCONCLUSIVE (a raw sample that does not exercise its mode, a native turn that did not complete or lacks what the shape needs, an ambiguous usage match, a script error, no SUMMARY line, a census exit status of 2): the INCONCLUSIVE requests or turns are repeated once, as a smaller invocation with the same argument vector and the missing count, in a quieter window; for a census INCONCLUSIVE the repeat is the whole acceptance (a new idle receipt, the four arms, a new census), because the census judges the window, not a request;
  a repeat that is again INCONCLUSIVE counts as NOT ACCEPTED. The scripts print their value-free diagnostics for every such turn (event types, stdout and stderr tails, the rows stored under the session id); they stay in the folder with the run.
- VOID (the gateway's identity changed during a run, was unreadable, or was not the build under test): a restart of the unit, a change of prefix or a failed health read during the acceptance means the build under test was not stable: roll back.
- Roll back at once (`python3 switch_gateways.py --rollback <the switch directory it printed>`, which restarts only 20128 to the baseline prefix) on any of: a FAIL (an effort group FAILs when an observed effort column differs from the baseline's observed value; an unobserved attempt is not a difference); a VOID; a health failure of the unit; a `Failed to save call log` line; NOT ACCEPTED; no complete acceptance within 2 hours of the switch.
  The failed run is kept as recorded.
- After ANY rollback: `gateway-identity.py --expect-prefix omniroute-3.8.51-2f42a9ac-pr13788-affinity2-pr15167 --expect-build cf6748d04` must exit 0 (health ok), `show-log-receipt.py` is run again, and 20129 must still run `omniroute-3.8.51-2f42a9ac-pr13788` (`87c4c488d`). 20129 is not switched at any point.
- After a pass, the unit's journal is scanned over 30 minutes of normal lane traffic (the journal command above): zero `Failed to save call log` lines, and the receipt after the switch shows the same drop-in declaration, a new `MainPID`, health ok and no credential-shaped strings except the known `[ModelSync]` account labels.

## Queueing

The PR is queued only after every gated request and turn of the canary passed at both reads (the wrapper's exit status 0), the census passed (exit 0), the 30-minute journal scan is clean and the after-switch receipt is recorded, all in `checks/`. On a FAIL, a VOID or a rollback the record is amended first (the candidate was rolled back, why, with the failed run kept as recorded) and the PR is not queued on the strength of "the results are in".
A canary that passed only as a no-regression check (the pre-switch control found the race set unable to discriminate) is recorded as that and does not support adoption.

## Records kept

For every run: the exact argument vector, the working directory, the start and end times, the script sha256 (all on the `FROZEN` line), the exit code (the `SUMMARY` line, `exit=` and `RUN-STATUS`), the identity before and after, the journal count, the pending-counter delta and the full stdout, as `checks/live-acceptance-canary-*.txt` next to the baselines
(the committed copy shortens UUID-shaped correlation ids to their first 8 hex digits, because the repository's publication check rejects full UUIDs, and starts with a note carrying the sha256 of the unshortened text; the unshortened outputs of the baselines, the controls and the canary are kept gzipped in the first host's private artifact directory and listed with their sha256 in `checks/logs/MANIFEST.txt`). The idle receipt and the census receipt are kept as `checks/live-acceptance-canary-guard-idle.txt` and `checks/live-acceptance-canary-census.txt` (the census prints ids as 8 hex characters only).
The unit's state before and after the switch is kept value-free (`systemctl --user show` fields, the receipts, the identity lines). Failed, inconclusive and void runs stay in the folder.
