The proposal needs material corrections. Its central rc5 failure claim is contradicted by the pinned source. I treated the truncated Tastytrade check as incomplete and excluded it from the findings.

1. **The stated IBKR blocker is refuted at the pin.** Issue #4983 reports **v1.227.0**, not rc5. At the exact proposed commit `1b0a49d…`, the execution engine checks `handles_order_venue`, and the IB adapter overrides that method to return `true`. Therefore, the claimed unconditional `IB`/`SMART` rejection does not follow from the pinned implementation. This does **not** establish broker acceptance; change the rationale to an unqualified native execution boundary rather than a verified occurrence of this defect. Sources: [issue #4983](https://github.com/nautechsystems/nautilus_trader/issues/4983), [pinned engine](https://raw.githubusercontent.com/nautechsystems/nautilus_trader/1b0a49d2792a9432a3aca3fcb617ce7a630d905e/crates/execution/src/engine/mod.rs), [pinned IB client](https://raw.githubusercontent.com/nautechsystems/nautilus_trader/1b0a49d2792a9432a3aca3fcb617ce7a630d905e/crates/adapters/interactive_brokers/src/execution/core.rs).

2. **The proposed “unchanged” rc5 trial cannot run as written.** The local harness explicitly requires Nautilus **1.231.0** and ibapi **10.45.1**; another version returns `refused_unpinned_runtime`. I evaluated its isolated, side-effect-free version predicate: 1.231.0 passed; rc5 failed. Create a version-specific rc5 harness retaining the acceptance contract. Also, the existing 1.231.0 receipt covers accept/cancel/fill/flatten—not the outstanding reconnect, restart-reconciliation and kill-switch gates. Sources: [local runtime guard](blueprints/us-equities/engine-nautilus/ibkr-paper-orders/run.py:1678), [current qualification boundaries](catalogs/us-equities/runtime-target.json:51), [rc5 integration interface](https://raw.githubusercontent.com/nautechsystems/nautilus_trader/v2.0.0rc5/docs/integrations/interactive_brokers.md).

3. **ML4T is a credible trial candidate, but the trial recipe omits a material incompatibility.** Its **v0.1.12** limitations explicitly exclude dividend accounting and automatic corporate-action adjustments. The frozen SPY contract requires ex-date dividend cash, while the existing comparator binds receipts to Nautilus’s version and sealed manifest. A `lean` preset cannot establish those mappings. Specify a separate receipt/mapping implementation and dividend treatment before calling this an executable parity trial. Sources: [pinned ML4T limitations](https://raw.githubusercontent.com/ml4t/backtest/v0.1.12/LIMITATIONS.md), [local comparator](blueprints/us-equities/engine-nautilus/spy-parity/compare.py:299), [frozen mapping](blueprints/us-equities/engine-nautilus/spy-parity/mapping-manifest-v2.json).

4. **A strong omitted candidate is IBKR’s official Python synchronous wrapper.** Rejecting the stale PyPI `ibapi` mirror is justified, but the supported upstream distribution is different. IBKR documents its sync wrapper in TWS API **10.40 onward**, explicitly supports it, and invites paper testing while identifying it as beta. Evaluate that native option separately from both the stale mirror and `ib_async`; it is especially relevant because this repository already uses official ibapi. Source: [IBKR’s announcement and distribution clarification](https://www.interactivebrokers.com/campus/?p=233474).

5. **LEAN’s IBKR execution plugin deserves an explicit challenger disposition.** The proposal checks its metadata but considers LEAN only as an oracle. Upstream PR #265 reports actual IB paper tests from a Python LEAN algorithm, including SPY/QQQ and contingent orders. That is relevant upstream evidence, although it is not this repository’s acceptance. Include it in the comparison with its documented module-subscription and deployment prerequisites. Sources: [IBKR plugin paper-test report](https://github.com/QuantConnect/Lean.Brokerages.InteractiveBrokers/pull/265), [installation requirements](https://github.com/QuantConnect/Lean.Brokerages.InteractiveBrokers).

6. **The Clear Street rejection contains factual errors.** Clear Street publishes an installable, Apache-2.0 Python Studio SDK and documents a demo environment with simulated fills and replayed market data. Thus, “not an installable OSS SDK” and “cannot be evaluated further without opening an account” are untenable for source review. Demo access eligibility remains unestablished. Exclusion because it is outside the selected broker scope remains reasonable. Sources: [official SDK](https://github.com/clear-street/studio-sdk-python), [demo documentation](https://docs.clearstreet.io/studio/docs/sandbox).

7. **Two other rejection descriptions need updating.** ThetaGang now supports direct share and regime-based equity rebalancing, including a configuration that does not enable options writing. Alpaca MCP v2 is a FastMCP/OpenAPI rewrite whose dependencies do not include `alpaca-py`; it also supports server-side selection of data-only toolsets. Neither automatically belongs in the execution service, but “options-wheel only” and “same alpaca-py wrapper requiring another writer before any use” overstate the exclusions. Sources: [ThetaGang capabilities](https://github.com/brndnmtthws/thetagang), [MCP configuration](https://github.com/alpacahq/alpaca-mcp-server), [pinned MCP dependencies](https://raw.githubusercontent.com/alpacahq/alpaca-mcp-server/v2.3.2/pyproject.toml).

8. **LEAN’s capability drift is real, but its Alpaca attribution is too broad.** #9822 adds **options** combo orders. Engine-wide contingent-order support includes OUO, but Alpaca’s brokerage model permits OCO and OTO, composing brackets from those; it does not list OUO. Distinguish engine support, brokerage-model validation and separately versioned plugin implementation. Sources: [combo change](https://github.com/QuantConnect/Lean/pull/9822), [Alpaca model](https://raw.githubusercontent.com/QuantConnect/Lean/master/Common/Brokerages/AlpacaBrokerageModel.cs), [Alpaca plugin change](https://github.com/QuantConnect/Lean.Brokerages.Alpaca/pull/83).

The adaptive trial’s retained output and broker readback match their recorded hashes and show five orders, four fills, one cancellation and flat reconciliation. Retaining those components for that demonstrated scope is defensible; it establishes neither comparative superiority nor continuous-operation acceptance.
