Retain DuckDB as the local baseline, but revise the proposal’s factual claims, rejection rationale, and comparison tests. I independently opened the sources below; I did not run comparative benchmarks.

1. **The Iceberg “refutation” is incorrect.** DuckDB has an official Iceberg extension supporting reads and catalog-backed writes. Polars documents `scan_iceberg`, including a native reader. Their absence from Iceberg’s illustrative README list proves neither incompatibility nor reliance exclusively on third-party connectors. Check supported features at pinned revisions instead. Sources: [DuckDB Iceberg](https://duckdb.org/docs/current/core_extensions/iceberg/overview), [Polars scan_iceberg](https://docs.pola.rs/api/python/stable/reference/api/polars.scan_iceberg.html).

2. **The concurrency argument misses an upstream candidate: Quack.** DuckDB supports concurrent writer threads within one process. Its official Quack extension also provides client/server access from multiple processes. Quack remains beta, so it needs a separate qualification decision, but the blanket single-writer characterization is inaccurate. Include it in the concurrency comparison. Sources: [concurrency](https://duckdb.org/docs/current/connect/concurrency), [Quack’s beta status](https://duckdb.org/docs/current/quack/overview).

3. **Scope `earns_it` to the demonstrated workload.** DuckDB 1.5.5 checks out, and the retained study provides meaningful local-execution evidence. However, 12 GB is a configured buffer-manager limit, not DuckDB’s dataset-size ceiling or a process-RSS cap. DuckDB also supports spilling to disk. The 13.1 GB observation does not establish an impending capacity failure or superiority over challengers. Sources: [release](https://github.com/duckdb/duckdb/releases/tag/v1.5.5), [memory-limit semantics](https://duckdb.org/docs/current/configuration/pragmas), [out-of-core execution](https://duckdb.org/docs/current/guides/performance/how_to_tune_workloads).

4. **DuckLake’s defects do not justify gating Iceberg’s trial.** The upstream reports warrant caution about DuckLake, but concern its implementation and catalog behavior. Iceberg should receive an independent test. Also, the opened body of #1215 identifies DuckDB **1.5.3 and main**, rather than establishing the proposal’s specific “still loses deletes on 1.5.5” claim. Supply the exact supporting comment or reproduction, including extension revision and catalog backend. Sources: [#1215](https://github.com/duckdb/ducklake/issues/1215), [#1404](https://github.com/duckdb/ducklake/issues/1404).

5. **XTDB has not been decisively eliminated by citing existing time travel.** XTDB explicitly models row-level valid time and system time. ArcticDB also advertises bitemporal versioning, so neither automatic superiority nor equivalence should be assumed. Compare late corrections, backfills, and unknown availability under one frozen contract. Storage cannot invent missing historical provenance, but temporal query behavior remains an implementation question. Sources: [XTDB temporal model](https://docs.xtdb.com/concepts/key-concepts.html), [ArcticDB’s documented claims](https://arcticdb.io/faqs/).

6. **Spark and Ray are rejected using faulty criteria.** Spark supports `local[*]`; it requires neither a cluster nor Iceberg to process data. JVM overhead can justify deferral, but “full JVM cluster” cannot. Ray Data provides data processing separately from Ray Serve. Rejecting Ray because it is not storage, while admitting Dask into “storage-compute,” applies inconsistent criteria. Sources: [Spark execution modes](https://spark.apache.org/docs/latest/submitting-applications.html), [Ray Data](https://docs.ray.io/en/latest/data/data.html).

7. **Lance’s rejection overlooks a relevant capability.** Its primary README documents automatic versioning, ACID transactions, time travel, tags, and branches. Those capabilities directly intersect the proposed snapshot trials. The unverified random-access benchmark is reasonably excluded, but it is insufficient grounds to dismiss the entire candidate. Source: [Lance README](https://github.com/lance-format/lance/blob/main/README.md).

8. **Add stronger comparison coverage.** **delta-rs** offers Rust/Python Delta tables and versioned reads without Spark; it is already catalogued locally but omitted from this proposal. **DataFusion Python** offers embedded, multithreaded SQL/DataFrame execution over Arrow and Parquet. **Polars streaming** deserves a direct memory-comparison arm before adding Dask solely for memory concerns. These are source-supported candidates, not measured winners. Sources: [delta-rs versioned reads](https://github.com/delta-io/delta-rs/blob/python-v1.6.4/docs/usage/loading-table.md), [DataFusion Python](https://datafusion.apache.org/python/), [Polars streaming](https://docs.pola.rs/user-guide/concepts/streaming/).

9. **The proposed equality tests need repair.** The local `results.json` includes elapsed time, run timestamp, engine version, code hash, and inspection history; literal equality across implementations is unsuitable. The 45,406,248 events are derived study events, not the input Parquet row count, and the input is privately retained. Freeze input hashes and a canonical result contract, separating runtime metadata and file serialization from analytical equality. ArcticDB’s versioned DataFrame read also does not promise reconstruction of original Parquet bytes. Sources: [local result construction](blueprints/us-equities/broad-universe/evaluate.py:920), [DuckDB nondeterminism](https://duckdb.org/docs/current/operations_manual/non-deterministic_behavior), [ArcticDB API](https://docs.arcticdb.io/latest/api/library/).

10. **The server trials do not adequately test their claimed advantages.** Requiring a `clickhouse-local` speed win before testing concurrent writers can exclude a useful server for an unrelated reason. Separately, ReplacingMergeTree provides eventual deduplication; correction-sensitive queries require appropriate query-time handling. Test concurrency, correction visibility, recovery, and snapshot integrity independently, with explicit decimal schemas. QuestDB supports exact decimals, but its default precision/scale is **18,3**, which does not satisfy the repository’s **38,12** contract automatically. Sources: [clickhouse-local](https://clickhouse.com/docs/concepts/features/tools-and-utilities/clickhouse-local), [ReplacingMergeTree correctness](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/replacingmergetree), [QuestDB decimals](https://questdb.com/docs/query/datatypes/decimal/).
