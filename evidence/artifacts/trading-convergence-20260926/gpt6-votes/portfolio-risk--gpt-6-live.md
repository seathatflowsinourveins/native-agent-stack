1. **High — The proposal’s evidence baseline is obsolete.** September 23 records already contain skfolio CPCV/covariance execution, MeanRisk/HRP allocations with reconciled Nautilus P&L, and cvxportfolio, empyrical-reloaded and QuantStats execution. They also record skfolio weights passing through Nautilus limits, including a $59,784.13 order denied against a $45,000 cap. I checked the referenced artifact hashes and inspected retained outputs. This refutes “zero native execution” and “no connection”; broker reconciliation remains a separate limitation. Sources: [candidate execution](evidence/artifacts/gap-wave2-20260923/us-equities__portfolio-risk/1-candidate-libs-execution.json:74), [optimizer accounting](evidence/artifacts/gap-wave2-20260923/us-equities__portfolio-risk/10-nautilus-optimizer-pnl.json:33), [risk-limit results](evidence/artifacts/gap-wave2-20260923/us-equities__portfolio-risk/6-nautilus-riskengine-denial.json:34). These are historical execution records, not newly reproduced runs.

2. **High — The skfolio upgrade trial cannot run unchanged.** The six releases and VaR/EVaR fixes check out. However, `evaluate.py` explicitly rejects versions other than `1.2.9`, and `plan.json` embeds that version. Updating the declared version necessarily changes the plan hash. Create a separately frozen upgrade experiment and compare semantic results; requiring an unchanged plan hash would preserve incorrect provenance. Sources: [upstream releases](https://github.com/skfolio/skfolio/releases), [version guard](blueprints/us-equities/research-evaluation/evaluate.py:182), [frozen version](blueprints/us-equities/research-evaluation/plan.json:15).

3. **High — The pyhrp comparison is underspecified and can flag legitimate differences as defects.** At the proposed `v2.3.3`, `hrp()` accepts **prices**, calculates percentage changes internally, and defaults to `bisection=False`. Skfolio accepts returns and explicitly performs optimal leaf ordering followed by recursive bisection. Matching Ward linkage and distance settings does not align those algorithms. Specify input conversion, ordering, allocation semantics and analytical reference cases before imposing `1e-6` agreement. Sources: [pyhrp pinned implementation](https://raw.githubusercontent.com/tschm/pyhrp/v2.3.3/src/pyhrp/hrp.py), [skfolio pinned implementation](https://raw.githubusercontent.com/skfolio/skfolio/v1.4.0/src/skfolio/optimization/cluster/hierarchical/_hrp.py).

4. **Medium — pyhrp’s claimed exclusive cross-check capability is false.** PyPortfolioOpt exposes `HRPOpt`, including code reproduced with López de Prado’s permission; Riskfolio implements `HCPortfolio` with HRP. Both merit consideration as independent implementation comparisons. Rejecting PyPortfolioOpt for lacking sklearn orchestration while promoting pyhrp for a narrow allocation comparison applies inconsistent criteria. Sources: [PyPortfolioOpt HRP documentation](https://pyportfolioopt.readthedocs.io/en/latest/OtherOptimizers.html), [Riskfolio implementation](https://raw.githubusercontent.com/dcajasn/Riskfolio-Lib/master/riskfolio/src/HCPortfolio.py).

5. **High — Riskkit’s proposed pass criterion would accept demonstrably inadequate validation.** In a reviewer-authored synthetic probe using the unchanged `v0.4.2` validator class bodies, both cases returned `passed=True` with no failed checks: negative equity, and a position worth **$100,000** carrying a caller-supplied **$100** notional. These results are deterministic and reproducible—the proposal’s stated pass conditions. Require expected rejection outcomes and consistency checks between price, quantity, notional and account state. This was an isolated source probe, not an installed-package acceptance or upstream-suite run. Source: [pinned validator](https://raw.githubusercontent.com/HasibVortex369/riskkit/v0.4.2/src/riskkit/validator.py).

6. **Medium — Riskfolio’s rejection contains two unsupported inferences.** An empty GitHub Releases listing does not make a package unauditable: PyPI supplies versioned source distributions and checksums, and the repository maintains a changelog. Conversely, a paid course syllabus listing walk-forward/CPCV topics does **not** establish that the installable library exports those facilities. Mark that capability unverified until an implementation and callable API are identified. Sources: [PyPI release artifacts](https://pypi.org/project/riskfolio-lib/7.3.0/), [changelog](https://raw.githubusercontent.com/dcajasn/Riskfolio-Lib/master/CHANGELOG.rst), [course page](https://riskfolio-lib.readthedocs.io/en/latest/course/course.html).

7. **Medium — Several “off-requirement” descriptions are materially incomplete.** Fincore `0.5.1`, released September 20, includes risk models and an implemented `walk_forward_var`; ffn includes `calc_mean_var_weights` and `calc_erc_weights`; factorlasso supplies factor-covariance estimation. These capabilities directly concern allocation or risk estimation. They do not establish superiority, but “reporting only” or blanket exclusion from portfolio risk is unjustified. Sources: [fincore release](https://pypi.org/project/fincore/0.5.1/), [release-bound VaR implementation](https://raw.githubusercontent.com/cloudQuant/fincore/576459c495a8f7ff839f55e0d3057daa636174cc/fincore/risk/diagnostics.py), [ffn allocation implementations](https://raw.githubusercontent.com/pmorissette/ffn/master/ffn/core.py), [factorlasso](https://github.com/ArturSepp/factorlasso).

8. **Medium — Rejections need capability comparisons, not release-cadence proxies.** Cvxportfolio provides multi-period optimization with cost objectives and time-dependent constraints—a substantive comparison target beyond sklearn compatibility. Its alleged absence of native evidence is also contradicted by finding 1. For riskparityportfolio, the missing matching tag establishes an unresolved source-to-release mapping, not that identification is impossible; PyPI publishes a hash-addressable `0.6.0` source distribution. Sources: [cvxportfolio policies](https://www.cvxportfolio.com/en/stable/optimization_policies.html), [riskparityportfolio artifacts](https://pypi.org/project/riskparityportfolio/0.6.0/).

9. **Omissions — Compare against native enforcement and an independent optimization reference.** Nautilus `v2.0.0rc5` already contains the relevant pre-trade `RiskEngine`; it should be the explicit baseline for assessing riskkit’s additional value. **PortfolioAnalytics** is another serious omitted comparison: constrained portfolio optimization plus rolling/expanding rebalancing are implemented upstream. Its R runtime and GPL-3 license are concrete adoption tradeoffs; it can still serve as an independent numerical reference. Sources: [pinned Nautilus engine](https://raw.githubusercontent.com/nautechsystems/nautilus_trader/v2.0.0rc5/crates/risk/src/engine/mod.rs), [PortfolioAnalytics on CRAN](https://cran.r-project.org/web/packages/PortfolioAnalytics/index.html), [rebalancing implementation](https://raw.githubusercontent.com/braverock/PortfolioAnalytics/master/R/optimize.portfolio.R).
