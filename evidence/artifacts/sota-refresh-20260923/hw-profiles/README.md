## Summary

- Both new components are additions, not upgrades of an existing pin, so there
  is no prior receipt to diff against; `mlx-lm-hash-lock.json` is marked
  `not_comparable` for that reason rather than `qualified`/`regression`.
- `scripts/hardware_profile.py` was measured on this host and its
  recommendation output matches a written-in-advance expectation exactly
  (`hardware-profile-tool.json`'s `preregistration` block, timestamped before
  the run). This host is a WSL laptop: 24 logical cores, `.wslconfig`
  `memory=48GB` (confirmed by reading `/mnt/c/Users/example/.wslconfig`
  directly), and an NVIDIA GeForce RTX 5090 Laptop GPU reporting 23.9 GB VRAM
  via `nvidia-smi` (the brief's "24 GB" is the marketing figure; the framebuffer
  nvidia-smi reports is slightly lower, which does not change the recommended
  tier since the threshold is `>=20GB`).
- `adoption/hardware-profiles.json` additionally records the 128 GB WSL
  workstation and 48 GB / 64 GB macOS arm64 unified-memory hosts as
  `labelled_projection` entries with inline sizing arithmetic (not
  measurements), and reserves a `github-macos-15-arm64-runner` entry to be
  filled with `native_proven` data the first time
  `.github/workflows/hardware-profile-smoke.yml` actually runs on a macOS
  runner -- this unit authored and offline-validated that workflow but did not
  execute it (no macOS host available in this worktree/sandbox).
- The mlx-lm pin (`0.30.2`) was independently confirmed to be uv's own
  resolver choice for `aarch64-apple-darwin` at both Python 3.12 and 3.13,
  even when unconstrained; ml-explore/mlx-lm's actual newest GitHub release is
  `v0.31.3` (`gh api repos/ml-explore/mlx-lm/releases/latest`, published
  2026-04-22), which uv does not select for this target -- recorded per the
  "qualify the newest release" instruction even though the pin does not use
  it.
- A reproducibility bug was caught and fixed during evidence-gathering: the
  first `uv pip compile --emit-index-url -o <path>` lock file was not
  byte-identical across output paths because uv's autogenerated header comment
  embeds the `-o` value, which would have made the CI job's "recompile and
  diff" verification step in `hardware-profile-smoke.yml` fail
  unconditionally. Fixed by switching to `--no-header` in both the committed
  lock file and the workflow step; a second run then produced a byte-identical
  file (`diff -q`, exit 0). See `mlx-lm-hash-lock.json`'s `results` field.
