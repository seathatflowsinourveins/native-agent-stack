# Notification types, the push notification bell and tmux (2026-09-29)

The checks behind the "Update 2026-09-29 (late)" section of [the terminal decision](../../../docs/decisions/2026-09-28-terminal-experience.md) and its
[receipt](../../receipts/notification-types-20260929.json). Each is read-only apart from the private temporary directories it removes (the replacement script writes only
the settings file it is pointed at, after a backup, and only with `--apply`); each prints booleans, counts and generic names only. Run them with `python3 -B` so no
`__pycache__` appears here. Each was run on the workstation the receipt names.

| Script | What it measures | How it was run |
| --- | --- | --- |
| `notification_types_scan.py` | Every Notification type the installed native Claude Code binary knows: the matcher values of the Notification event (a 15-item base array plus `elicitation_complete` and `elicitation_response`) and the `notificationType:"<type>"` literals at emitting call sites (a lower bound: other emit sites use other spellings). It holds `DECISIONS`, the one table the repository's test also imports: each type is `ring` or `quiet`, with whether the hooks reference documents it and its reason. A type with no entry is `UNKNOWN`, and a decision that disagrees with the overlay's matcher is reported; either makes the script exit 1 | `python3 -B notification_types_scan.py [<binary>] <checkout>` (from a checkout; the default binary is `~/.local/bin/claude`) |
| `push_notification_probe.py` | Whether a model-initiated PushNotification raises a `Notification` hook event, of which type, whether a bell hook for that type rings, and which branch of the client's presence rule decided (the terminal's focus report when it has reported focus, otherwise input within the last 60 s; read from the binary). A real interactive session in a pty (Haiku); the model runs `sleep N`, then calls the tool; the probe waits for the client to enable focus reporting before it types, prints whether it sent a focus-out report and the seconds from Enter to the tool call, and a BEL counter that follows Windows Terminal's output state machine counts the bell bytes after the tool call. Derived from `evidence/artifacts/terminal-experience-20260928/alert_probe.py` (sha256 prefix `1282ff2b` at the derivation): the `push` kind, `--bell-hook`, `--no-user-settings`, `--sleep`, `--no-focus-report`, the focus-out report and the timing lines are the additions. `--selftest` checks the counter | arms A `push --no-user-settings`, B `... --bell-hook`, C `push` (the user's own settings), D `... --no-focus-report --sleep 75`, E `... --no-focus-report --sleep 15` |
| `tmux_bell_probe.py` | Whether tmux passes a pane's BEL to the outer terminal, so the bell still rings for an agent-team lead in a tmux pane: a private tmux server with an empty configuration, a client in a Python pty (which stands for Windows Terminal only in that a bare BEL is what the hook writes), five arms (default, `bell-action any` set explicitly, `bell-action none` as the negative control, `visual-bell on`, a pane that prints no BEL) | `python3 -B tmux_bell_probe.py` (needs tmux) |
| `replace_bell_group.py` | How the settings files were brought to the overlay when its matcher changed: the repository's merge tool never changes the matcher of a group that already runs the bell command, so the script removes that group on a private copy, merges the overlay again with the repository's own tool, checks that only the bell group differs (the whole Notification list, every other event and key), and with `--apply` installs the copy atomically after a backup (`local`, or `polaris` through `wsl.exe`). It refuses a bell group that holds another hook, two bell groups, a symlinked file and an unknown target, finds a hand-requoted spelling of the bell command, and exits nonzero on a failed write or read-back. Rerun after the change it reports "nothing to do" | `python3 -B replace_bell_group.py <checkout> local|polaris [--apply]` |
| `replace_bell_group_controls.py` | Nine cases for the script above, each a subprocess against a synthetic `HOME` (never a real settings file): the safe cases succeed (an old matcher, a hand-requoted bell command, a file with no bell group, a file that already matches, an unrelated group beside the bell group) and the unsafe ones are refused | `python3 -B replace_bell_group_controls.py <checkout>` |

Not retained: the raw hook payloads of the probes (session ids, paths), which the probe removes, and the coordinator's own output of the same probe on this host's settings before the change, which is recorded in the
receipt as values.
