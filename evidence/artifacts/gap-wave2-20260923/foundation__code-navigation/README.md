## Gap 0 — matched cross-candidate benchmark (source/reference completeness, cost)

Ran a bounded, single-symbol probe (`capture_jcodemunch` in
`tools/ecosystem/token_manifest.py` of the agent-lab canonical checkout,
commit `c042ea7` on branch `codex/native-expansion` with a dirty working tree
at probe time — recorded exactly in the receipt's `probed_checkout` field)
against an rg gold set (1 definition + 3 references, one of which is a
dynamic-import `m.capture_jcodemunch(...)` call that a static-LSP backend
cannot resolve to the real symbol). Serena's `find_referencing_symbols`
returned only the same-file bare call (1/3 gold references); jCodeMunch's
`search_symbols` returned the exact definition plus name-substring matches
but zero call-site references (it is a definition-name search, not a
reference search, so this is not a fair apples-to-apples recall comparison
against Serena). codebase-memory-mcp is confirmed removed from this host as
of 2026-09-21 (`docs/tasks/2026-09-21-codebase-memory-removal-log.txt`, `git
show e0b8b2e`), so it is structurally excluded from any three-tool benchmark
on this host right now, not merely untested. No token-cost accounting was
captured in this pass. The receipt discloses that the rg gold-set line
numbers were established before the preregistration text was written (the
comparison design was decided first; only those numbers are post-hoc).
Outcome: **advanced** — narrows the gap with one real completeness data
point and a concrete failure mechanism (dynamic import defeats static
reference resolution), but does not settle the full preregistered
multi-language, three-tool, cost-scored benchmark the gap calls for.

## Gap 1 — symbol rename/delete correctness per index or language server

**Round 1** attempted to test Serena's `rename_symbol`/`safe_delete_symbol`
against a disposable scratch repo via a standalone
`serena start-mcp-server --project <disposable-repo> --transport
streamable-http` process, and reported a false incident: that doing so
mutated the shared, host-wide `~/.serena/serena_config.yml` read by every
concurrently running Serena instance, and that this could not be fully
reverted. Neither claim held up: the live Serena MCP servers on this host run
with `SERENA_HOME=/home/example/.local/share/codex-ecosystem/context/serena-home`
(confirmed via `/proc/<pid>/environ`), so none of them reads
`~/.serena/serena_config.yml`; and that file did not exist before round 1
(Serena's own log says it was autogenerated), so the four paths round 1
created under `~/.serena` (`language_servers/`, `logs/`, `prompt_templates/`,
`serena_config.yml`) were fully revertible by deletion, which round 2 did
(after backing them up to this unit's own cache directory). Because of the
false hazard, round 1 never issued a single rename/delete call.

**Round 2** set `SERENA_HOME` to an isolated directory under
`/home/example/.cache/gap-wave2-20260923/code-navigation/` and instantiated a
Serena agent in-process (no MCP server, no network port) against the
already-indexed disposable repo, then called `RenameSymbolTool` on
`compute_total -> compute_grand_total` and `SafeDeleteSymbol` on `report`.
Results: rename left zero stale-name hits, the new name resolved correctly,
and the in-file call site inside `Basket.total` was updated too; delete left
zero hits for `report` and removed its body from the file. `~/.serena/`
(the real, shared one) stayed unchanged — only `memories/` — before and after
the run, confirmed by directory listings.

Outcome: **advanced** — settles the correctness assertion for Serena on
Python in this disposable repo (rename and delete both behave correctly and
survive reindex), but jCodeMunch (no identified rename/delete/reindex action
in its read-only, time-boxed session surface) and codebase-memory-mcp
(absent from host since 2026-09-21) remain unevaluated, so the full
preregistered three-tool claim is not fully settled.
