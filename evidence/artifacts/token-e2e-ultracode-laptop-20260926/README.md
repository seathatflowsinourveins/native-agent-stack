Host: `wsl-authoring-20260923`, the WSL2 authoring laptop. Measurement window: 00:35:58Z to 01:13:57Z. Catalog revision: `9a8257cd` (detached worktree `nas-e2e-R`, origin/main).
Machine-readable record: [`receipt.json`](receipt.json).

This reproduces the workstation's own catalog evidence (`evidence/artifacts/token-e2e-ultracode-20260925/receipt.json`, PR #296) on a second host, reusing 13 of that receipt's 16 tool tasks unchanged (`reference-tasks.json`) and adding a second, independent verification pass this workstation run did not have. The other 3 (codebase-memory-mcp, agentsview, otel-tui) are not part of this run; see Method and "Retained failures and gaps" for why each was left out.

## Question

Does each of 13 of the reference's 16 tools run inside an Ultracode workflow subagent on this laptop? When it does, what do the tool's own lifetime counters, an exact tokenizer, and an independent second subagent agree on?

Installing and configuring a tool does not show any saving. This run makes one claim per tool, and each claim has three parts, not two:

- a Sonnet 5 subagent used the tool on real work, and a check against a plain baseline confirmed its answer;
- the saving comes from the tool's own counter, where the tool has one, and from an exact tokenizer comparison of the same information need;
- an independent Opus 5.5 subagent reproduced the check from the same files and either confirmed or refuted the first subagent's report.

## Method

1. **Reuse, not rewrite.** The 13 tools and their tasks are the workstation's own reference tasks (`reference-tasks.json`, copied verbatim from PR #296's receipt). Where the reference's exact target does not exist on this host, or this host's own instructions name a different one, the e2e subagent recorded the change under `deviations_from_reference` rather than silently substituting. 3 of the reference's 16 tools are not among these 13: `codebase-memory-mcp` was actively removed from this host's own selected profile on 2026-09-21 (a competent `trace_path` comparison found no capability over the already-registered Serena/SocratiCode lanes it did not duplicate; `docs/tasks/2026-09-21-codebase-memory-removal-log.txt`, decision in `docs/tasks/2026-09-21-consensus-resolutions.md` section 3); `agentsview` (v0.43.0) and `otel-tui` (v0.7.5) simply have no task in `reference-tasks.json` as handed to this run -- likely because PR #296 itself recorded both as observation-only, with no baseline/tool-output pair (`exact_comparison: null` for both; its own README lists them as "observation only" / "none" for token count and savings) -- though ai-memory also has `exact_comparison: null` there and is still one of the 13, so pairlessness is not the whole story. Both remain installed and reachable on this host (confirmed live via `command -v`).
2. **Before snapshot** at 00:35:58Z: `rtk gain` globally and project-scoped, `headroom savings --json`, jCodeMunch's persistent ledger, Context Mode's stats file, and this host's own token-evidence refresh.
3. **e2e pass.** 13 Sonnet 5 workflow subagents (label `e2e:<tool>`), one per tool. Each:
   - worked against a disposable detached worktree `R` = `nas-e2e-R` at `9a8257cd` (origin/main), or the session project root (`agent-lab`) where a tool is bound to it;
   - wrote the baseline only by shell redirect or an equivalent read-only extraction;
   - read only the tool's own output;
   - answered from that output;
   - ran one deterministic PASS/FAIL check of the answer against the baseline.
4. **verify pass.** 13 independent Opus 5.5 workflow subagents (label `verify:<tool>`), one per tool, each working only from the e2e subagent's own pair files (`baseline.txt`, `tool-output.txt`, `answer.txt`, `check.txt`, unchanged). Each verifier reproduced the deterministic check, re-ran the tool's own channel where feasible, checked the installed binary/package against its upstream release, and returned a verdict (`confirmed` or `refuted`) with supporting notes. Several verifiers also recorded exceptions the e2e worker itself had not disclosed: context-mode's worker had already seen its target file's own `## ` heading count from an earlier command before the tool call (`tools[].verifier.notes`, context-mode); jCodeMunch's worker had seen the answer's signature and line number in an earlier Bash `grep`, and made one extra, unlisted read-only `menu()` call (jcodemunch); ai-memory's worker read `baseline.txt` before writing its own check, contradicting its stated blind protocol (ai-memory). In each case the verifier confirmed the answer still followed from the tool's own output regardless, so the conclusion is unaffected — see each tool's `verifier.notes` in `receipt.json` for the exact evidence.
5. **After snapshot** at 01:13:57Z. Then every baseline/tool-output pair was compared exactly with the pinned `o200k_base` tokenizer and recorded in a private host-side ledger (`token-evidence/ledger.sqlite3`), and `child-usage.mjs` read the provider usage of every child.
6. **Role probes.** Three role-scoped subagents (`source-scout`, `evidence-reviewer`, `isolated-builder`) each tried the same lanes (RTK, QMD, Serena, SocratiCode, jCodeMunch, Context Mode, ai-memory) to record which lanes each role's own tool allowlist can reach, separate from whether the tool itself works. This field (`role_access_probes`) has no equivalent in PR #296; it is new here and explained below.

### What `baseline_kind` means

`baseline_kind` is a field PR #296 does not have; it is added here because several of this host's `tokens_removed` values are negative, and a negative number means two different things depending on what `baseline.txt` actually is:

- **`counterfactual_raw`** — `baseline.txt` is the real content the tool made unnecessary to read in full: the same commands' unfiltered raw output (rtk), the actual source file (jCodeMunch, ast-grep), the actual document (QMD, Context Hub, MarkItDown), or the actual data being compressed/encoded (Headroom, TOON). When `tokens_removed` is positive here, it is a genuine reduction for this one task.
- **`check_ground_truth`** — `baseline.txt` is a small fixture built only to verify the tool's answer: a `grep`/`git grep` excerpt (Serena: definition line + call sites; Repomix: `grep -n '^def '` over the real file; SocratiCode: `grep -n -A 12` over the real function), or a direct SQL/API extraction used purely as ground truth (ai-memory: `COUNT(*)` queries against the SQLite store; Context Mode: an independent `grep` reproduction of the expected summary, not the 73 KB source file). These baselines are always much smaller than the real counterfactual would be, so `tokens_removed` is negative by construction and **must never be read as a savings shortfall** — the tool was never being compared against the real thing it replaces, only checked for correctness.

Three `counterfactual_raw` tools (Headroom, QMD, TOON) still show a negative `tokens_removed`, for a third, distinct reason: the captured `tool-output.txt` bundles more than the efficient representation alone. Headroom's holds the compress **and** retrieve **and** stats responses together (the retrieve step echoes the full original content back). QMD's holds the preceding search-result listing plus qmd's own per-line numbering overhead on top of the retrieved document. TOON's holds both the encoded TOON body **and** the decoded-back JSON from the strict round-trip check. None of these are check-only fixtures — the baseline is the genuine raw counterfactual — but the specific artifact this host's pair captured is not an apples-to-apples "compressed size" claim either.

**Only the five tools whose `tokens_removed` is both positive and `counterfactual_raw`** (RTK, jCodeMunch, ast-grep, Context Hub, MarkItDown) may be read as a measured reduction for this task, and two of those five carry their own qualification:

- **RTK's +250,247** is a real, verifier-reproduced size reduction (94.3% of bytes), but not "no fact lost": the verifier refuted that specific claim (see "Retained failures and gaps" — the CMD2 branch misclassification, and 599 of its hidden-match recall pointers being shortened excerpts rather than full lines).
- **Context Hub's +256,669** compares against a 761,734-byte baseline that is the *raw HTML of the live upstream page, scripts included*, not isolated prose; the verifier's own check, like the worker's, was scoped to whether two specific facts (retry count, timeout) appear verbatim in that page — neither check was scoped as a token-savings measurement.

## Retained failures and gaps

- **RTK, refuted:** the verifier reproduced the worker's own check (13/13 PASS) and its measured savings (94.3% of bytes, 51.6% of lines), and confirmed the channel is genuine — the installed binary's sha256 matches the upstream `rtk-ai/rtk` v0.50.0 release asset, `rtk hook claude` is the registered PreToolUse hook, and `rtk verify` shows 154/154 internal tests passing. It refuted the worker's "no fact lost" claim on two specific points. First, rtk v0.50.0's `filter_branch_output` (`src/cmds/git/git_cmd.rs` lines 3185-3244) keeps the `+ ` linked-worktree marker on local branches, so `git branch -a`'s reported "remote-only (31)" is really only 6 true remote-only branches; 25 of the 31 are local branches checked out in a linked worktree. Second, the host's `^git show [^ ]*:` exclude pattern only matches the bare `git show REV:path` form; the `-C DIR` form this run actually used (`git -C R show HEAD:README.md`) is rewritten anyway, so that exclusion does not hold as documented. The verifier also found 599 of rtk's recall pointers for its hidden grep matches are shortened excerpts, not full lines, even with `--full`. Because of these findings, RTK's +250,247/93.5% figure (see the table above) is a measured size reduction only, not a "no fact lost" compaction. **Both exclude-pattern gaps are mitigated on this laptop on 2026-09-26: two added exclude patterns, anchored to the git subcommand position (see the sibling rtk-exclude-widen PR's recipe); a separate catalog PR carries that recipe change, not this evidence artifact.** Post-fix verification (`rtk-exclude-check-20260926.txt`, retained privately on the host, sha256 in `receipt.json`, reflecting the 02:03Z anchored-pattern state): every tested form of `git [-C p] show REV:path` and `git [-C p] branch -a` now goes native, while `show --stat`, `status`, `ls` and `grep` are still rewritten, and `rtk verify` still passes 154/154. These patterns later gained `--git-dir`/`--work-tree` in the global-option group at 02:40Z, after this check was recorded; the sibling rtk-exclude-widen PR carries the final patterns.
- **Serena:** `find_referencing_symbols` missed 6 of 8 real project-wide call sites of `summarizeRun` (it found only the 2 references inside the same file, `.claude/workflows/child-usage.mjs`, missing all 6 in `.claude/workflows/test-child-usage.mjs`). The worker attributed this to agent-lab having no root `tsconfig.json`/`jsconfig.json` — **the verifier's own controlled experiment against the installed language server confirms this causal link is real** (an explicit `.claude/workflows/*.mjs` include raises the count to 9 of 9), but also found the worker's own check had only established the config files' *absence*, not the causal link itself, and that a *default*-include tsconfig/jsconfig would not have fixed it (TypeScript's include wildcards skip dot-directories; an explicit `.claude` include is required). A correctly configured Serena would return 9 references, not the reference task's expected 8, so this check's own count-equality design would still fail even after such a fix.
- **Repomix 1.18.1 `--compress`:** packing `scripts/host_requests.py` silently dropped the top-level function `def status_body` (a signature spanning 3 physical lines, ending its first line on a bare keyword-only `*,`) from the structural extraction, with no visible sign anything was missing — 47 of 48 real top-level functions were present and correct. Root cause, confirmed against the installed and current upstream source: `getFunctionSignature` only tests a `def`'s first physical line; when that regex fails on a multi-line signature, the whole function is silently discarded. The verifier reproduced the same gap on `credential_status.py`'s `inspect` (also a multi-line signature) and on a minimal test fixture; no upstream issue reports this. **The verifier also found that the workstation's own reference receipt (PR #296) recorded this identical repomix pack and task as `count=47 PASS` — that receipt's repomix result is a false pass on the same real gap found here.** Recommended as a follow-up, not part of this PR: an erratum to the `token-e2e-ultracode-20260925` artifact noting the corrected repomix verdict.
- **SocratiCode:** `codebase_search` returned no hits from any file under the dot-directory `.claude/`, even though `codebase_symbols` and the code graph do index it. Confirmed against installed upstream source: this project's `.mcp.json` sets `INCLUDE_DOT_FILES=false`, and upstream's semantic/embedding search index honors that setting while the separate code-graph walker does not.
- **Context Hub:** `chub cache status` returned Bash exit code 1 while printing a normal-looking, successful status report. The verifier's rerun of the same command did not reproduce the nonzero exit on either an isolated or the real cache directory, and the installed CLI's status code path has no `exit(1)` in it — recorded as an unresolved, non-blocking discrepancy, not a confirmed defect.
- **codebase-memory-mcp, agentsview, otel-tui:** the workstation reference (PR #296) ran all 16 of these tools; only 13 are reused here. `codebase-memory-mcp` was actively removed from this host's own selected profile on 2026-09-21 — a competent `trace_path` comparison found no capability over the already-registered Serena/SocratiCode lanes it did not duplicate, so its mcporter registration and 286 MB prefix were removed reversibly (`docs/tasks/2026-09-21-codebase-memory-removal-log.txt`; decision in `docs/tasks/2026-09-21-consensus-resolutions.md` section 3, reinstall recipe retained). `agentsview` (v0.43.0) and `otel-tui` (v0.7.5) both remain installed and reachable on this host (confirmed live via `command -v agentsview` / `command -v otel-tui`) but have no task in `reference-tasks.json` as handed to this run; the likely reason is that PR #296 itself recorded both as observation-only, with no baseline/tool-output pair (`exact_comparison: null` for both, and its own README table lists them as "observation only" / "none"), though ai-memory has the same `exact_comparison: null` there and is still one of the 13, so pairlessness alone does not fully explain the selection.
- **Codex:** not run in this evidence pass. The account's usage limit runs until 2026-09-30 23:50, per this host's own token-evidence record — a carried fact, not a fresh probe from this workflow.
- **Self-corrected within a single attempt (no restart needed):** ai-memory's first baseline script compared a text-string page id against ai-memory's SQLite BLOB id column and got `PAGE_NOT_FOUND`; fixed by encoding the id as raw UUID bytes before the query. QMD's check construction hit one false FAIL from a mis-escaped grep literal in an early ad-hoc test; corrected and re-run to PASS. MarkItDown's deterministic check first reported 1 of 19 assertions FAIL (`--scope local` not found) because the live docs page's syntax highlighter splits that literal across two HTML `<span>` tags in the raw byte stream; re-run against a mechanically tag-stripped copy (a byte transform, not a reading of the baseline's content) gave 19 of 19 PASS. Headroom's first two content choices both hit real no-op protective routes in the installed source rather than exercising compression; a third, larger real file did exercise it and is what is reported.

## Reproduce

Follow `tools/token-report/README.md` for the ledger conventions this host reused. `receipt.json`'s `tools[].task` is the workstation's own reference-task wording (PR #296, copied verbatim as `reference-tasks.json`), not this run's own literal commands; this run's actual adaptation, channel and findings are in `tools[].deviations_from_reference`, `tools[].answer_excerpt`, `tools[].quality_check` and `tools[].verifier`. The baseline and tool-output artifacts are kept by sha256 in the private host-side ledger and are not committed: several are derived from a read-only detached worktree or third-party pages, and all of them can be regenerated from the stated commands.
